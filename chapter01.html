🔷 Что такое паттерны проектирования?

Что такое паттерны проектирования?

Краткий ответ: Паттерны проектирования (Design Patterns) — это типовые, проверенные временем способы решения часто встречающихся задач при проектировании программ. Это не готовый код и не библиотека, а идея организации классов и объектов, которую можно реализовать на любом языке, включая Java.

Развёрнутое объяснение

Представьте, что вы строите дом. Если вам нужна лестница, никто не изобретает ее заново — используют известную конструкцию, адаптируя ее под конкретный дом. С паттернами происходит то же самое.

Зачем нужны паттерны:

  • писать код, который легче поддерживать;
  • уменьшить связанность между классами;
  • сделать код более гибким для изменений;
  • использовать общий язык с другими разработчиками.

Например, вместо длинного объяснения можно сказать: «Здесь лучше использовать Factory». И опытный Java-разработчик сразу поймет общую идею решения.

Самая известная книга по этой теме — "Design Patterns: Elements of Reusable Object-Oriented Software" (1994). Ее написали четыре автора, которых называют Gang of Four (GoF). Именно они описали 23 классических паттерна.

Какие категории паттернов существуют?

Краткий ответ: Три категории: порождающие (Creational) — как создавать объекты, структурные (Structural) — как соединять объекты, и поведенческие (Behavioral) — как объекты взаимодействуют.

1. Порождающие (Creational)

Отвечают на вопрос: Как создавать объекты?

Singleton, Factory Method, Abstract Factory, Builder, Prototype.

// Singleton — создает только один объект класса
public class Database {
    private static final Database INSTANCE = new Database();
    private Database() {}
    public static Database getInstance() { return INSTANCE; }
}

// Builder — когда объект содержит много параметров
User user = User.builder()
    .name("Иван").age(25).city("Москва").email("ivan@mail.ru").build();

// Factory Method — создание объекта передается фабрике
Animal animal = AnimalFactory.create("dog"); // фабрика решает, какой объект создать

2. Структурные (Structural)

Отвечают на вопрос: Как соединять объекты между собой?

Adapter, Decorator, Proxy, Composite, Facade, Bridge.

// Adapter — старый класс работает с новым интерфейсом
class PrinterAdapter implements Printer {
    private OldPrinter printer;
    public void print() { printer.printOld(); }
}

// Decorator — добавляет функциональность без изменения класса
Coffee coffee = new SimpleCoffee();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);

// Facade — один простой класс для сложной системы
CarFacade.start(); // внутри вызывает Engine, FuelSystem, Battery...

3. Поведенческие (Behavioral)

Отвечают на вопрос: Как объекты взаимодействуют друг с другом?

Strategy, Observer, Command, State, Iterator, Template Method, Chain of Responsibility, Mediator.

// Strategy — несколько алгоритмов, легкая замена
interface PaymentStrategy { void pay(); }
class CardPayment implements PaymentStrategy {}
class PaypalPayment implements PaymentStrategy {}

// Observer — один объект сообщает изменения многим другим
observer.update(); // подписчики получают уведомление

// Command — каждое действие оформляется отдельным объектом
Command command = new SaveCommand();
command.execute(); // можно хранить, отменять, ставить в очередь

🔶 Порождающие паттерны (Creational)

💎 Singleton (Одиночка)

Краткий ответ: Singleton гарантирует, что у класса будет только один экземпляр, и предоставляет глобальную точку доступа к нему. Сколько бы раз вы ни пытались создать объект, всегда будет использоваться один и тот же экземпляр.

Зачем нужен Singleton

Представьте класс настроек приложения. Если каждый раз создавать новый объект Settings s1 = new Settings(); Settings s2 = new Settings();, получится два независимых экземпляра. Изменения в одном не попадут в другой. Это неправильно для: конфигурации, логирования, кэша, менеджера подключений, счетчика статистики.

Базовая реализация

public class Singleton {
    // Единственный экземпляр
    private static final Singleton INSTANCE = new Singleton();
    // Запрещаем создавать объект извне
    private Singleton() {}
    // Получить экземпляр
    public static Singleton getInstance() { return INSTANCE; }
}

Разбор по частям:

  • private static final Singleton INSTANCE = new Singleton(); — private (никто не обратится напрямую), static (принадлежит классу), final (ссылку нельзя изменить), new (создается один раз при загрузке класса).
  • private Singleton() {} — конструктор закрыт, new Singleton() не скомпилируется: Singleton() has private access.
  • public static Singleton getInstance() — единственный способ получить объект.

Как это выглядит в памяти

Singleton.class
    | INSTANCE
    v
+----------------+
| Singleton      |
+----------------+
// Singleton a, b, c — все ссылаются на один объект

Ленивая инициализация (Lazy Initialization)

public class Singleton {
    private static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

Объект создается только при первом вызове getInstance(). Проблема: не потокобезопасен — два потока могут увидеть instance == null и создать два объекта.

Где применяется: настройки приложения, логгер, кэш, менеджер конфигурации. В Spring бины по умолчанию singleton scope.

Как реализовать потокобезопасный Singleton

Способ 1: Double-Checked Locking

public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

Способ 2: Bill Pugh Holder (рекомендованный)

public class Singleton {
    private Singleton() {}
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

Потокобезопасен благодаря JLS: класс Holder загружается только при первом обращении, JVM гарантирует атомарность инициализации статических полей, final обеспечивает безопасную публикацию объекта.

Способ 3: Enum Singleton (лучший по Джошуа Блоху)

public enum Singleton {
    INSTANCE;
    public void doWork() { /* Полезная логика */ }
}

Автоматически защищен от многопоточности, рефлексии и сериализации.

Double-checked locking — подробно

public static Singleton getInstance() {
    if (instance == null) { // Первая проверка (без блокировки) — быстрый путь
        synchronized (Singleton.class) {
            if (instance == null) { // Вторая проверка (с блокировкой) — гарантия
                instance = new Singleton();
            }
        }
    }
    return instance;
}

Зачем volatile: предотвращает проблему reordering. Без volatile поток мог бы получить ссылку на еще не полностью сконструированный объект (операция new не атомарна: выделение памяти → инициализация полей → присвоение ссылки; JVM может переупорядочить).

Решение: в современной Java-разработке используют Dependency Injection (Spring). Зависимости передаются явно через конструктор, код легко тестировать, жизненным циклом управляет контейнер.

// Вместо Singleton — внедрение зависимости
@Service
public class UserService {
    private final Database database;
    public UserService(Database database) { this.database = database; }
}
🏭 Factory Method vs Abstract Factory

Краткий ответ: Factory Method создаёт один продукт, Abstract Factory — семейство связанных продуктов. Оба относятся к порождающим паттернам и решают задачу создания объектов, но на разных уровнях.

Factory Method

Идея: предоставить метод, который создает объект, а выбор конкретного класса оставить наследникам. Отвечает на вопрос: Какой объект создать?

Структура

Product               Creator
   ▲                  + factoryMethod()
   │                      ▲
ConcreteProductA           │
ConcreteProductB    ConcreteCreatorA
                    ConcreteCreatorB

Пример: уведомления

interface Notification { void send(); }

class EmailNotification implements Notification {
    public void send() { System.out.println("Email"); }
}
class SmsNotification implements Notification {
    public void send() { System.out.println("SMS"); }
}

abstract class NotificationFactory {
    public abstract Notification createNotification();
}
class EmailFactory extends NotificationFactory {
    public Notification createNotification() { return new EmailNotification(); }
}
class SmsFactory extends NotificationFactory {
    public Notification createNotification() { return new SmsNotification(); }
}

// Использование
NotificationFactory factory = new EmailFactory();
Notification notification = factory.createNotification();
notification.send(); // Email

Когда использовать: один тип продукта с разными реализациями (Document, Animal, Payment).

Abstract Factory

Идея: создавать целое семейство связанных объектов. Отвечает на вопрос: Как создать совместимый набор объектов?

Пример: GUI для Windows и Mac

interface Button { void paint(); }
interface Checkbox { void paint(); }

class WindowsButton implements Button {
    public void paint() { System.out.println("Windows Button"); }
}
class WindowsCheckbox implements Checkbox {
    public void paint() { System.out.println("Windows Checkbox"); }
}
class MacButton implements Button {
    public void paint() { System.out.println("Mac Button"); }
}
class MacCheckbox implements Checkbox {
    public void paint() { System.out.println("Mac Checkbox"); }
}

interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}
class WindowsFactory implements GUIFactory {
    public Button createButton() { return new WindowsButton(); }
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}
class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// Использование
GUIFactory factory = new WindowsFactory();
factory.createButton().paint();    // Windows Button
factory.createCheckbox().paint();  // Windows Checkbox

Главное отличие

Factory MethodAbstract Factory
Создает один продуктСоздает семейство продуктов
Обычно один метод созданияНесколько методов создания
Использует наследованиеИспользует композицию
Выбирает конкретную реализациюВыбирает набор совместимых объектов

Связь между ними

Abstract Factory часто реализуется через несколько Factory Method. Каждый метод (createButton, createCheckbox) — это Factory Method, а их объединение в одном интерфейсе образует Abstract Factory.

Аналогия

Factory Method: «Сделайте мне автомобиль» — завод решает какой, получаете одну машину.

Abstract Factory: «Мне нужен полный комплект BMW» — фабрика выдает двигатель, коробку передач, салон, электронику. Все детали совместимы. Если выбрать Mercedes — весь комплект будет Mercedes.

Когда использовать

Factory Method: один тип объектов, заранее неизвестен конкретный класс, убрать new из клиентского кода.

Abstract Factory: объекты создаются группами и должны быть совместимы, легкое переключение между семействами (Windows/Mac, PostgreSQL/MySQL, Light/Dark Theme), гарантия что клиент не смешает несовместимые реализации.

👷 Builder (Строитель)

Краткий ответ: Builder используют, когда объект сложно создать одним конструктором. Он позволяет создавать объект поэтапно и делает код более читаемым.

Проблема длинных конструкторов

// Без Builder: что означает каждый параметр?
new User("Misha", "misha@mail.com", 30, null, null, true);
// Что такое true? Что означает null? При десяти параметрах легко ошибиться.
// С Builder: код читается как обычный текст
User user = User.builder()
    .name("Misha")
    .email("misha@mail.com")
    .age(30)
    .active(true)
    .build();

Пример реализации

public class User {
    private final String name;
    private final String email;
    private final int age;

    private User(Builder builder) {
        this.name = builder.name;
        this.email = builder.email;
        this.age = builder.age;
    }

    public static class Builder {
        private String name;
        private String email;
        private int age;

        public Builder name(String name) { this.name = name; return this; }
        public Builder email(String email) { this.email = email; return this; }
        public Builder age(int age) { this.age = age; return this; }

        public User build() {
            if (name == null) {
                throw new IllegalStateException("Name required");
            }
            return new User(this);
        }
    }
}

// Использование
User user = new User.Builder()
    .name("Alex")
    .email("alex@mail.com")
    .age(25)
    .build();

Когда Builder действительно нужен

  1. Много параметров конструктора — Car.builder().engine(e).color("Black").sunroof(true).build();
  2. Большинство параметров необязательные — User.builder().name("Alex").build(); или User.builder().name("Alex").phone("123").address("London").build();
  3. Объект должен быть неизменяемым (Immutable) — все поля final, безопасно для многопоточности.
  4. Нужна проверка перед созданием — в методе build() проверяем обязательные поля.
  5. Создание состоит из нескольких этапов — HttpClient.newBuilder().connectTimeout(...).followRedirects(...).build();

Когда Builder не нужен

Если класс простой (new Point(x, y)) или параметров 2-3 (new Employee(id, name)) — Builder только усложнит код.

🧬 Prototype (Прототип)

Краткий ответ: Prototype — порождающий паттерн, который создает новые объекты путем копирования (клонирования) существующего экземпляра, а не через new. Используется, когда создание объекта дорогое или сложное, либо когда заранее неизвестен точный тип объекта.

Когда использовать

  • создание объекта занимает много времени или ресурсов;
  • объект имеет большое количество полей и сложную инициализацию;
  • нужно создавать множество похожих объектов с небольшими изменениями;
  • конкретный класс объекта может определяться только во время выполнения.

Реализация в Java

// Конструктор копирования — наиболее рекомендуемый вариант
class User {
    private String name;
    private Address address; // вложенный объект

    public User(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    // Конструктор копирования
    public User(User other) {
        this.name = other.name;
        this.address = new Address(other.address); // глубокое копирование
    }
}

User user1 = new User("Misha", new Address("Moscow"));
User user2 = new User(user1); // независимая копия

Поверхностное и глубокое копирование

  • Shallow copy (поверхностная): копируются примитивы, ссылки копируются как есть, вложенные объекты остаются общими. Изменение вложенного объекта в копии затронет оригинал.
  • Deep copy (глубокая): копируются все вложенные объекты, новая копия полностью независима от оригинала. Именно необходимость глубокого копирования — одна из сложностей Prototype.

Плюсы и минусы

Плюсы: ускоряет создание сложных объектов, уменьшает дублирование кода, позволяет создавать объекты без привязки к конкретным классам.

Минусы: сложно реализовать глубокое копирование, Cloneable и Object.clone() считаются неудачным API в Java, необходимо внимательно копировать изменяемые объекты.

Prototype vs Builder

Prototype копирует уже существующий объект. Builder пошагово собирает новый объект с нуля.
