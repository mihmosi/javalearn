Полный справочник по внутреннему устройству HashMap, контракту equals/hashCode и смежным темам. Каждый раздел содержит краткий ответ и развёрнутое объяснение с примерами кода на Java.

🔷 Устройство HashMap

Как устроена HashMap внутри?

Краткий ответ: HashMap — это массив корзин (buckets), каждая из которых представляет собой связный список или красно-чёрное дерево. Ключ-значение хранится в виде объекта Node. Индекс корзины вычисляется как hash(key) & (capacity - 1). При достижении порога загрузки массив увеличивается вдвое.

Структура хранения

class Node {
    final int hash; final K key; V value; Node next;
}

С Java 8 корзина может быть: пустой (null), односвязным списком Node, или корнем красно-чёрного дерева TreeNode (когда список > 8 элементов).

Вычисление индекса корзины

int hash = key.hashCode();
hash = hash ^ (hash >>> 16);  // XOR-шифтинг для лучшего распределения
int index = hash & (table.length - 1); // побитовое И с маской

Почему capacity — степень двойки (16, 32, 64...)? Вычитание единицы даёт битовую маску, а & работает как быстрый аналог hash % capacity.

Что такое bucket (корзина) в HashMap?

Краткий ответ: Bucket — это ячейка внутреннего массива Node<K,V>[] table. В одной корзине может быть null (пустая), голова связного списка, или корень красно-чёрного дерева.

// Визуализация
[0] → null                           // пустая
[1] → Node("a") → Node("b")          // связный список
[2] → TreeNode("c")                  // красно-чёрное дерево

Индекс корзины вычисляется как hash & (capacity - 1). При capacity=16 разные ключи могут дать одинаковый индекс (коллизия). Условия деревофикации: ≥ 8 элементов в корзине И capacity ≥ 64.

Как HashMap определяет, в какой bucket положить элемент?

Краткий ответ: index = (key.hashCode() ^ (key.hashCode() >>> 16)) & (table.length - 1). Двухшаговый процесс: XOR-шифтинг + побитовое И с маской.

XOR-шифтинг "впечатывает" старшие биты hashCode в младшие, улучшая распределение. Побитовое И с маской (capacity-1) работает как быстрый аналог деления по модулю. Для null-ключа индекс всегда 0.

Что такое коллизия в HashMap?

Краткий ответ: Коллизия — ситуация, когда два разных ключа получают одинаковый индекс корзины. Элементы объединяются в цепочку (связный список или дерево).

Два вида коллизий: (1) разные hashCode → одинаковый индекс из-за маски; (2) одинаковый hashCode (редко, например "Aa" и "BB" → 2112). При поиске сначала сравнивается хеш (быстрое сравнение int), затем equals (только при совпадении хешей).

Как HashMap обрабатывает коллизии?

Краткий ответ: Методом цепочек (separate chaining). Элементы с одинаковым индексом связываются через поле next. До Java 8 — только список, с Java 8 — список до 8 элементов, затем дерево.

При поиске цепочка обходится последовательно: сначала хеш, потом equals. Деревофикация при ≥ 8 элементах и capacity ≥ 64 защищает от деградации O(n). При ≤ 6 элементах дерево → обратно в список.

Что происходит при достижении 8 элементов в одном bucket?

Краткий ответ: Если capacity < 64 → resize() (расширение массива). Если capacity ≥ 64 → treeifyBin() (связный список → красно-чёрное дерево, O(log n) вместо O(n)).

Порог 8 выбран на основе распределения Пуассона: вероятность 8 элементов в одной корзине при хорошем hashCode ≈ 0.00000006. Обратное преобразование (untreeify) при ≤ 6 элементах.

🟠 Контракт equals() и hashCode()

Что такое контракт equals() и hashCode()?

Краткий ответ: Набор правил из Javadoc Object. Главное: если a.equals(b) == true, то a.hashCode() == b.hashCode() обязательно. Обратное не требуется. Нарушение ломает HashMap/HashSet.

Контракт equals()

ПравилоОписание
Рефлексивностьx.equals(x) всегда true
Симметричностьx.equals(y) == y.equals(x)
Транзитивностьx.equals(y) и y.equals(z) → x.equals(z)
КонсистентностьПовторные вызовы — один результат
null-безопасностьx.equals(null) всегда false

Правильный шаблон

@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User)) return false;
    User u = (User) o;
    return Objects.equals(id, u.id) && Objects.equals(name, u.name);
}
@Override public int hashCode() {
    return Objects.hash(id, name); // те же поля!
}
Если два объекта равны по equals(), что можно сказать об их hashCode()?

Краткий ответ: Их hashCode() обязан быть одинаковым. Это жёсткое требование контракта. Нарушение → объект "теряется" в HashMap (equals=true, но лежит в другой корзине).

HashMap сначала ищет корзину по hashCode. Разные hashCode → разные корзины → equals никогда не вызывается.

Если два объекта имеют одинаковый hashCode(), обязательно ли они равны по equals()?

Краткий ответ: Нет, не обязательно. Это коллизия — нормальная ситуация. HashMap обрабатывает её через цепочки.

Контракт требует только прямого следствия (equals=true → hashCode одинаковый), но не обратного. Пример: "Aa" и "BB" — hashCode одинаковый (2112), equals=false.

Что будет если переопределить equals() но не hashCode()?

Краткий ответ: Объекты, равные по equals, будут иметь разные системные хеш-коды. HashMap/HashSet сломаются: get() → null, contains() → false, можно добавить "дубликаты".

Причина: HashMap сначала ищет корзину по hashCode (разный → разные корзины), equals не вызывается.

Что будет если переопределить hashCode() но не equals()?

Краткий ответ: Объекты попадут в одну корзину (hashCode совпадает), но equals сравнивает ссылки (Object.equals). Логически одинаковые объекты считаются разными ключами.

HashMap добавит их как отдельные элементы в цепочку, HashSet допустит дубликаты. Формально контракт hashCode не нарушен, но поведение некорректно.

🟢 Ключи HashMap

Можно ли использовать изменяемый объект как ключ в HashMap?

Краткий ответ: Формально можно, практически — нельзя. Если после вставки меняются поля equals/hashCode, ключ "теряется" (memory leak).

Безопасно изменять только поля, не участвующие в equals/hashCode. Лучшая практика: только неизменяемые ключи (String, Integer, UUID, LocalDate, enum).

Что случится, если изменить ключ после добавления в HashMap?

Краткий ответ: Ключ "потеряется". get() → null, containsKey() → false, но объект физически остаётся в карте, занимая память (memory leak).

Причина: HashMap вычисляет корзину в момент вставки и не пересчитывает при изменении ключа. Изменённый hashCode указывает на другую корзину.

Какие требования к ключу HashMap?

Краткий ответ: (1) Корректные equals/hashCode по контракту; (2) неизменяемость полей в equals/hashCode; (3) стабильный hashCode.

Идеальный ключ: final class с final полями, Objects.requireNonNull в конструкторе, одни и те же поля в equals и hashCode.

Почему String часто используется как ключ в HashMap?

Краткий ответ: String — идеальный ключ: иммутабельный, hashCode кешируется, эффективный equals, отличное распределение, реализует Comparable, final class.

Кеширование hashCode делает повторные вызовы мгновенными (O(1) после первого вычисления), что критично для производительности HashMap.

🔵 Параметры HashMap

Что такое load factor в HashMap?

Краткий ответ: loadFactor = 0.75 (по умолчанию). Определяет порог расширения: capacity × loadFactor. Компромисс между скоростью и памятью.

loadFactorПамятьКоллизии
0.5ИзбыточнаяМинимум
0.75СбалансированнаяНизкая
1.0ЭкономичнаяВысокая
Что такое capacity в HashMap?

Краткий ответ: capacity — размер внутреннего массива корзин (table.length), всегда степень двойки. Не путать с size (количество элементов).

При создании capacity округляется вверх до ближайшей степени 2. Формула выбора: expectedSize / 0.75 + 1.

Когда происходит rehashing в HashMap?

Краткий ответ: (1) Когда size > capacity × loadFactor; (2) при попытке деревофикации с capacity < 64 — вместо дерева resize.

Оба случая вызывают resize() — создание нового массива вдвое больше и перераспределение всех элементов.

Что происходит при rehashing?

Краткий ответ: Создаётся новый массив ×2, каждый элемент переносится с пересчётом индекса. Оптимизация: проверка одного бита hash & oldCap — 0 → та же корзина, 1 → oldIndex + oldCap.

Списки разделяются на lo-цепочку (оставшиеся) и hi-цепочку (перемещённые). Это O(n) операция.

Какова временная сложность операций get() и put() в HashMap?

Краткий ответ: В среднем — O(1). В худшем (без дерева) — O(n). С деревом (Java 8+) — O(log n).

ОперацияСреднийХудший (Java 7)Худший (Java 8+)
get/putO(1)O(n)O(log n)
removeO(1)O(n)O(log n)
resizeO(n)O(n)O(n)
Когда временная сложность может стать O(n)?

Краткий ответ: Когда все ключи попадают в одну корзину (плохой hashCode) и деревофикация не применяется (Java 7 или capacity < 64).

Также частые resize() из-за неправильной начальной ёмкости, хотя каждый отдельный get/put — O(1).

🟣 Многопоточность и альтернативы

Как работает HashMap в многопоточной среде?

Краткий ответ: HashMap НЕ потокобезопасен. Возможны: потеря элементов, зацикливание (Java 7), неверный size, NPE.

Зацикливание в Java 7 исправлено в Java 8 (lo/hi цепочки сохраняют порядок), но карта всё ещё не потокобезопасна. Для многопоточности: ConcurrentHashMap (рекомендовано), Collections.synchronizedMap(), внешний synchronized.

Что такое ConcurrentHashMap и чем он отличается от HashMap?

Краткий ответ: Потокобезопасная Map. В отличие от HashMap: CAS для пустых корзин, synchronized на уровне корзины, запрет null, атомарные операции, weakly-consistent итераторы.

null-ключи/значенияДаНет (NPE)
Атомарные операцииНетДа (putIfAbsent, compute...)

🟡 Null и сравнение реализаций

Можно ли хранить null ключ в HashMap?

Краткий ответ: Да, ровно один null-ключ. Он всегда в корзине №0 (hashCode = 0). ConcurrentHashMap и Hashtable запрещают.

Можно ли хранить null значение в HashMap?

Краткий ответ: Да, сколько угодно. Главная проблема: get() возвращает null и для отсутствующего ключа, и для ключа со значением null. Различать через containsKey().

В чём разница между HashMap и Hashtable?

Краткий ответ: HashMap — современная, несинхронизированная, разрешает null. Hashtable — устаревшая (Java 1.0), синхронизированная, запрещает null.

ХарактеристикаHashMapHashtable
ПотокобезопасностьНетДа (synchronized)
nullДаНет (NPE)
Когда появилсяJava 1.2Java 1.0
Что такое WeakHashMap?

Краткий ответ: Map, в которой ключи хранятся как WeakReference. Если на ключ нет сильных ссылок, GC удаляет запись. Полезно для кешей без риска memory leak.

Важно: строковые литералы никогда не удалятся (String Pool). Значения хранятся как сильные ссылки.

Как правильно выбрать начальный capacity для HashMap?

Краткий ответ: Формула: expectedSize / 0.75 + 1. Для 1000 элементов: 1000/0.75+1 = 1334 → округлится до 2048 (степень 2). Позволяет избежать resize().

Готовые решения: Guava Maps.newHashMapWithExpectedSize(), JDK 19+ HashMap.newHashMap().

Что лучше: ArrayList или HashMap для хранения пар ключ-значение?

Краткий ответ: HashMap — O(1) поиск. ArrayList — O(n). Для словарей всегда HashMap. ArrayList оправдан только для 1-3 элементов, дубликатов ключей, или когда поиск не нужен.
