Полный справочник по Stream API в Java: преимущества, intermediate и terminal операции, параллельные стримы, коллекторы, ленивые вычисления и многое другое. Каждый раздел включает краткий ответ и развёрнутое объяснение с примерами кода для уровня Middle+.

🔷 Основы Stream API

Какие преимущества даёт использование Stream API?

Краткий ответ: Stream API даёт декларативный, лаконичный код, эффективное выполнение за счёт ленивости и внутренней оптимизации, простой параллелизм "из коробки", композицию операций без промежуточных коллекций и чистоту функционального стиля без побочных эффектов.

1. Декларативность: ЧТО, а не КАК

// Императивный подход: КАК делать — циклы, условия, временные переменные
List<String> adultNames = new ArrayList<>();
for (User user : users) {
    if (user.getAge() >= 18) {
        String name = user.getName().toUpperCase();
        if (!adultNames.contains(name)) {
            adultNames.add(name);
        }
    }
}
Collections.sort(adultNames);

// Декларативный подход: ЧТО нужно — filter, map, distinct, sorted
List<String> adultNames = users.stream()
    .filter(user -> user.getAge() >= 18)
    .map(User::getName)
    .map(String::toUpperCase)
    .distinct()
    .sorted()
    .collect(Collectors.toList());

Декларативный код читается как спецификация: "взять пользователей → отфильтровать совершеннолетних → взять имена → заглавными → уникальные → отсортировать → собрать в список". Это радикально снижает когнитивную нагрузку при чтении и проверке кода.

2. Lazy evaluation и эффективность выполнения

Промежуточные операции не выполняются до вызова терминальной. Стрим строит план операций и выполняет их одним проходом по данным:

users.stream()
    .filter(u -> expensiveCheck(u))  // Не выполняется сразу
    .map(User::getName)               // Не выполняется сразу
    .limit(3)                         // Не выполняется сразу
    .collect(Collectors.toList());    // ВСЁ запускается здесь!

// Благодаря limit(3) — expensiveCheck выполнится не для всех пользователей,
// а только до нахождения трёх подходящих. Короткое замыкание!

3. Параллелизм "из коробки"

// Последовательный стрим
users.stream().filter(...).collect(...);

// Параллельный — меняем одно слово, использует ForkJoinPool
users.parallelStream().filter(...).collect(...);

Никакого ручного управления потоками: не нужно создавать Thread, ExecutorService, делить данные.

4. Композиция без побочных эффектов

// Без Stream API: побочные эффекты неизбежны
List<String> results = new ArrayList<>();
for (Item item : items) {
    if (item.isValid()) {
        results.add(transform(item));  // Мутация внешнего списка
    }
}

// Со Stream API: чистая композиция функций
List<String> results = items.stream()
    .filter(Item::isValid)
    .map(this::transform)
    .collect(Collectors.toList());  // Без внешних переменных, без мутаций

Отсутствие побочных эффектов означает: код легко тестировать, код потокобезопасен, рефакторинг безопасен, параллелизация безопасна.

В чём разница между intermediate и terminal операциями?

Краткий ответ: Intermediate (промежуточные) операции возвращают Stream и не выполняются до вызова терминальной (ленивые). Terminal (терминальные) операции возвращают НЕ Stream (коллекцию, Optional, примитив) или void, запускают выполнение всей цепочки и закрывают Stream.

Intermediate операции

  • Возвращают Stream — можно продолжать цепочку
  • Ленивые: не выполняются до вызова терминальной операции
  • Примеры: filter, map, flatMap, distinct, sorted, limit, skip, peek

Terminal операции

  • Возвращают НЕ Stream (коллекцию, Optional, примитив) или void
  • Запускают выполнение всей цепочки
  • После вызова Stream больше недоступен
  • Примеры: collect, forEach, reduce, count, anyMatch, findFirst
Stream<String> stream = names.stream()
    .filter(n -> n.startsWith("A"))  // intermediate — ещё не выполняется
    .map(String::toUpperCase);       // intermediate — ещё не выполняется

// Ничего не произошло до этого момента!

List<String> result = stream.collect(Collectors.toList());  // terminal — ЗАПУСК!

Что делает операция filter()?

Краткий ответ: filter() — это промежуточная операция, которая отбирает элементы потока по заданному предикату (условию). Возвращает новый Stream, содержащий только элементы, удовлетворяющие условию.

List<User> adults = users.stream()
    .filter(u -> u.getAge() >= 18)   // Только совершеннолетние
    .filter(User::isActive)           // Только активные
    .collect(Collectors.toList());

filter() принимает Predicate<T> — функцию, возвращающую boolean. Элементы, для которых предикат вернул false, исключаются из дальнейшей обработки. Можно использовать цепочку из нескольких filter() — каждый сужает поток.

Что делает операция map()?

Краткий ответ: map() — это промежуточная операция, которая преобразует каждый элемент стрима в другой элемент по заданной функции. Преобразование 1:1 — каждому элементу входного потока соответствует ровно один элемент выходного.

List<String> upperNames = users.stream()
    .map(User::getName)        // User → String
    .map(String::toUpperCase)  // String → String
    .collect(Collectors.toList());

map() принимает Function<T, R> — функцию преобразования типа T в тип R. Тип стрима меняется: Stream<User> → Stream<String>. Каждый элемент обрабатывается независимо.

Что делает операция collect()?

Краткий ответ: collect() — это терминальная операция, которая собирает элементы стрима в результирующую структуру (List, Set, Map, String и т.д.) с помощью Collector'а. Это основной механизм материализации результатов стрима.

// Сборка в коллекции
List<String> list = stream.collect(Collectors.toList());
Set<String> set = stream.collect(Collectors.toSet());

// Сборка в Map
Map<Long, User> byId = stream.collect(Collectors.toMap(User::getId, Function.identity()));

// Сборка строки
String joined = stream.collect(Collectors.joining(", "));

// Сборка с группировкой
Map<String, List<User>> byDept = stream.collect(Collectors.groupingBy(User::getDepartment));

collect() — это изменяемая редукция: в отличие от reduce(), которая создаёт новый объект на каждом шагу, collect() добавляет элементы в существующий контейнер, что значительно эффективнее для коллекций.

Что такое Collector и какие есть встроенные Collectors?

Краткий ответ: Collector — это интерфейс, описывающий стратегию мутабельной редукции элементов Stream в результирующий контейнер. Collectors — утилитный класс с набором готовых реализаций.

Интерфейс Collector<T, A, R>

public interface Collector<T, A, R> {
    Supplier<A> supplier();          // Создать новый аккумулятор
    BiConsumer<A, T> accumulator();  // Добавить элемент в аккумулятор
    BinaryOperator<A> combiner();    // Слить два аккумулятора (для parallel)
    Function<A, R> finisher();       // Преобразовать аккумулятор в результат
    Set<Characteristics> characteristics(); // Флаги оптимизации
}

Пример создания своего Collector'а

Collector<String, StringJoiner, String> toJsonArray = Collector.of(
    () -> new StringJoiner(", ", "[", "]"),
    StringJoiner::add,
    (left, right) -> { left.merge(right); return left; },
    StringJoiner::toString,
    Characteristics.CONCURRENT
);
Что делает операция flatMap()?

Краткий ответ: flatMap() — это промежуточная операция, которая преобразует каждый элемент в Stream и "сплющивает" все вложенные стримы в один плоский поток. Преобразование 1:N — одному элементу соответствует 0, 1 или много элементов в результирующем стриме.

// Список заказов → все товары из всех заказов
List<Item> allItems = orders.stream()
    .flatMap(order -> order.getItems().stream())  // Order → Stream<Item>
    .collect(Collectors.toList());

// Список предложений → все уникальные слова
List<String> words = sentences.stream()
    .flatMap(sentence -> Arrays.stream(sentence.split(" ")))
    .distinct()
    .collect(Collectors.toList());

// Работа с Optional в стриме (JDK 9+)
List<Order> orders = users.stream()
    .map(User::getLastOrder)           // Stream<Optional<Order>>
    .flatMap(Optional::stream)         // Stream<Order> — распаковка
    .collect(Collectors.toList());

flatMap() принимает Function<T, Stream<R>>. Каждый элемент превращается в поток, и все эти потоки объединяются в один. Это ключевое отличие от map(), который дал бы Stream<Stream<R>>.

В чём разница между map() и flatMap()?

Краткий ответ: map() делает преобразование 1:1 (один элемент → один элемент), flatMap() делает преобразование 1:N (один элемент → 0, 1 или много элементов) и "сплющивает" результат в один поток.

Сравнение

Критерийmap()flatMap()
СигнатураFunction<T, R>Function<T, Stream<R>>
Преобразование1:11:N
РезультатStream<R>Stream<R> (плоский)
Если бы flatMap был map—Stream<Stream<R>>
// map: список имён → список длин (1:1)
List<Integer> lengths = names.stream()
    .map(String::length)
    .collect(Collectors.toList());

// flatMap: список заказов → все товары (1:N)
List<Item> items = orders.stream()
    .flatMap(order -> order.getItems().stream())
    .collect(Collectors.toList());

🔶 Параллельные стримы

Что такое параллельные стримы?

Краткий ответ: Параллельные стримы — это стримы, которые обрабатывают элементы параллельно в несколько потоков, используя ForkJoinPool. Они автоматически разбивают источник на части, выполняют операции над каждой частью в отдельном потоке и объединяют результаты.

Как создать

// Из коллекции
list.parallelStream()

// Из любого стрима
stream.parallel()

// Проверка
stream.isParallel()

Как работает

  1. Источник данных разбивается на части (splitting)
  2. Каждая часть обрабатывается в отдельном потоке ForkJoinPool
  3. Результаты объединяются (combining)
  4. По умолчанию используется ForkJoinPool.commonPool() с числом потоков = количество ядер - 1
Когда использовать parallel streams?

Краткий ответ: Parallel streams эффективны для CPU-интенсивных задач на больших объёмах данных (сотни тысяч+ элементов), где операции stateless и независимы. Не использовать для I/O операций, маленьких коллекций и операций с побочными эффектами.

Когда ИСПОЛЬЗОВАТЬ

  • Большие объёмы данных (сотни тысяч+ элементов)
  • Операции CPU-интенсивные (сложные вычисления)
  • Операции stateless и независимые
  • Собственный ForkJoinPool для изоляции

Когда НЕ ИСПОЛЬЗОВАТЬ

  • Маленькие коллекции (оверхед на разбиение превышает выигрыш)
  • Операции с побочными эффектами (изменение общей переменной)
  • I/O операции (лучше асинхронность, CompletableFuture)
  • Операции, зависящие от порядка (findFirst vs findAny)
Как создать parallel stream?

Краткий ответ: Два способа: вызвать parallelStream() на коллекции или преобразовать существующий стрим методом parallel().

// Способ 1: из коллекции
List<String> list = List.of("a", "b", "c");
Stream<String> parallel = list.parallelStream();

// Способ 2: из существующего стрима
Stream<String> sequential = list.stream();
Stream<String> parallel = sequential.parallel();

// Способ 3: в собственном ForkJoinPool
ForkJoinPool customPool = new ForkJoinPool(4);
customPool.submit(() -> list.parallelStream()
    .filter(...)
    .map(...)
    .collect(Collectors.toList())
).get();
Какие потенциальные проблемы могут быть с параллельными стримами?

Краткий ответ: Состояние гонки при изменении внешних переменных, непредсказуемый порядок обработки, дедлоки при использовании synchronized, общий ForkJoinPool может быть занят, ThreadLocal может давать неожиданные результаты.

  • Состояние гонки: изменение общих переменных из лямбд
  • Непредсказуемый порядок: forEach в параллельном стриме не гарантирует порядок
  • Дедлоки: synchronized внутри стрима + ограниченный пул потоков
  • Общий пул: другие параллельные стримы или CompletableFuture занимают потоки
  • ThreadLocal: значения не переносятся между потоками
  • Оверхед на разбиение: для маленьких коллекций медленнее последовательного
Что такое ForkJoinPool и как он связан с parallel streams?

Краткий ответ: ForkJoinPool — это реализация ExecutorService для параллельного выполнения задач по принципу "разделяй и властвуй" (fork/join). Parallel streams по умолчанию используют общий ForkJoinPool.commonPool().

Связь с parallel streams

  • По умолчанию используется ForkJoinPool.commonPool()
  • Число потоков = Runtime.getRuntime().availableProcessors() - 1
  • Можно задать свой пул через системное свойство java.util.concurrent.ForkJoinPool.common.parallelism
  • Можно запустить стрим в собственном пуле через submit()
// Запуск parallel stream в собственном пуле
ForkJoinPool customPool = new ForkJoinPool(4);
customPool.submit(() -> {
    list.parallelStream()
        .filter(...)
        .collect(Collectors.toList());
}).get();
customPool.shutdown();

Work-stealing алгоритм

Потоки ForkJoinPool "воруют" задачи из очередей других потоков, когда свои закончены, обеспечивая максимальную утилизацию CPU.

Что такое побочные эффекты в Stream и почему их следует избегать?

Краткий ответ: Побочные эффекты — это изменение состояния вне стрима во время выполнения операций (модификация внешних коллекций, переменных, полей объектов). Их следует избегать, потому что они нарушают контракт функционального программирования, делают код непредсказуемым, ломают параллелизм и затрудняют тестирование.

// НАРУШЕНИЕ: побочные эффекты — изменение внешнего списка
List<String> results = new ArrayList<>();
users.stream()
    .filter(u -> u.getAge() > 18)
    .forEach(u -> results.add(u.getName()));  // Изменяет внешний список!

// ПРАВИЛЬНО: без побочных эффектов
List<String> results = users.stream()
    .filter(u -> u.getAge() > 18)
    .map(User::getName)
    .collect(Collectors.toList());

Почему избегать

  • В параллельных стримах — race condition
  • Нарушает контракт функционального программирования
  • Делает код менее предсказуемым и тестируемым
  • Может сломаться при смене реализации стрима

Можно ли изменять состояние внешних переменных?

Не рекомендуется. В последовательных стримах технически работает, но это плохая практика. В параллельных — гарантированный race condition. Всегда используйте collect() вместо forEach() с мутацией внешнего состояния.

🟢 Операции Stream API

Что делает операция reduce()?

Краткий ответ: reduce() — это терминальная операция, которая выполняет свёртку всех элементов стрима в одно значение с помощью ассоциативной бинарной операции. Это иммутабельная редукция — на каждом шагу создаётся новое значение.

// Сумма: reduce(начальное значение, бинарный оператор)
int sum = numbers.stream().reduce(0, Integer::sum);

// Без начального значения — возвращает Optional
Optional<Integer> max = numbers.stream().reduce(Integer::max);

// Полная форма: reduce(identity, accumulator, combiner)
int sum = numbers.parallelStream().reduce(0, Integer::sum, Integer::sum);

Три формы reduce()

  1. reduce(identity, accumulator) — с начальным значением, всегда возвращает значение
  2. reduce(accumulator) — без начального значения, возвращает Optional (пустой стрим → empty)
  3. reduce(identity, accumulator, combiner) — полная форма для параллельных стримов
В чём разница между reduce() и collect()?

Краткий ответ: reduce() — иммутабельная свёртка (создаёт новый объект на каждом шагу). collect() — мутабельная сборка (добавляет элементы в существующий контейнер). collect() эффективнее для коллекций, reduce() — для примитивных значений.

Критерийreduce()collect()
Тип редукцииИммутабельнаяМутабельная
Создание объектовНа каждом шагу новыйОдин контейнер на поток
Эффективность для коллекцийПлохая (O(n²))Хорошая (O(n))
Для параллелизмаcombiner создаёт новый объектcombiner сливает контейнеры
// reduce() для списков — плохо: создаёт новый список на каждом шагу
List<String> bad = stream.reduce(
    new ArrayList<>(),
    (list, s) -> { list.add(s); return list; },     // Мутация + новый объект
    (list1, list2) -> { list1.addAll(list2); return list1; }
);  // O(n²)!

// collect() — хорошо: мутабельная сборка
List<String> good = stream.collect(Collectors.toList());  // O(n)
Что такое операция peek() и когда её использовать?

Краткий ответ: peek() — это промежуточная операция для "подглядывания" за элементами стрима без их изменения. Предназначена ТОЛЬКО для отладки. Не использовать для модификации элементов в продакшене — поведение не гарантировано.

// Отладка: смотрим, какие элементы проходят через стрим
List<String> result = users.stream()
    .peek(u -> log.debug("Before filter: {}", u))
    .filter(u -> u.getAge() > 18)
    .peek(u -> log.debug("After filter: {}", u))
    .map(User::getName)
    .collect(Collectors.toList());

// ❌ Неправильно: изменение элементов через peek()
users.stream()
    .peek(u -> u.setProcessed(true))  // Побочный эффект! Не гарантировано!
    .collect(Collectors.toList());

В параллельных стримах порядок вызовов peek() не гарантирован. peek() может быть оптимизирован компилятором и не вызван вовсе для некоторых элементов.

Можно ли повторно использовать Stream?

Краткий ответ: НЕТ. После вызова терминальной операции стрим считается потреблённым и больше недоступен. Попытка повторного использования вызовет IllegalStateException.

Stream<String> stream = names.stream();
long count = stream.count();          // Ок — первая терминальная операция
List<String> list = stream.collect(); // IllegalStateException: stream already operated upon!

Решение: создать новый стрим от источника:

Supplier<Stream<String>> supplier = names::stream;
long count = supplier.get().count();
List<String> list = supplier.get().collect(Collectors.toList());
Что такое lazy evaluation в Stream?

Краткий ответ: Lazy evaluation (ленивые вычисления) — это свойство Stream API, при котором промежуточные операции не выполняются до вызова терминальной. Стрим "планирует" цепочку операций и выполняет их одним проходом по данным.

users.stream()
    .filter(u -> expensiveCheck(u))  // Не выполняется
    .map(User::getName)               // Не выполняется
    .limit(3)                         // Не выполняется
    .collect(Collectors.toList());    // ТУТ ВСЁ ЗАПУСКАЕТСЯ

// Благодаря limit(3) — expensiveCheck выполнится только до нахождения трёх подходящих

Когда начинается выполнение?

Только при вызове терминальной операции (collect, reduce, forEach, count, findFirst и т.д.).

Что это даёт

  • Оптимизация: не обрабатываются ненужные элементы (короткое замыкание)
  • Экономия памяти: не создаются промежуточные коллекции
  • Однопроходность: все операции выполняются за один проход по данным
Что делают операции distinct(), sorted(), limit(), skip()?

Краткий ответ: distinct() — удаляет дубликаты (по equals). sorted() — сортирует элементы. limit(n) — ограничивает поток первыми N элементами. skip(n) — пропускает первые N элементов. Все это intermediate-операции.

// distinct: уникальные элементы
List<String> unique = stream.distinct().collect(Collectors.toList());

// sorted: сортировка
List<String> natural = stream.sorted().collect(Collectors.toList());
List<User> byAge = stream.sorted(Comparator.comparing(User::getAge)).collect(Collectors.toList());

// limit: первые N
List<String> first10 = stream.limit(10).collect(Collectors.toList());

// skip: пропустить первые N
List<String> page2 = stream.skip(10).limit(10).collect(Collectors.toList()); // пагинация

Короткое замыкание (short-circuiting)

limit(n) — intermediate-операция с коротким замыканием: после получения N элементов обработка останавливается, даже если источник содержит больше элементов.

Как работает короткое замыкание в Stream?

Краткий ответ: Короткое замыкание (short-circuiting) — это механизм, при котором операция завершается досрочно, как только получен достаточный результат, не обрабатывая оставшиеся элементы.

Intermediate с коротким замыканием

  • limit(n) — прекращает обработку после N элементов

Terminal с коротким замыканием

  • anyMatch(predicate) — останавливается на первом true
  • allMatch(predicate) — останавливается на первом false
  • noneMatch(predicate) — останавливается на первом true
  • findFirst() — нужен только первый элемент
  • findAny() — нужен любой элемент
// anyMatch: останавливается на первом подходящем
boolean hasAdmin = users.stream()
    .anyMatch(User::isAdmin);  // Не проверяет всех, если админ найден быстро

// limit + filter: эффективно вместе
List<String> first3Adults = users.stream()
    .filter(u -> u.getAge() >= 18)
    .limit(3)
    .collect(Collectors.toList());  // Останавливается после 3 найденных
Что такое операции anyMatch(), allMatch(), noneMatch()?

Краткий ответ: Это терминальные операции с коротким замыканием, проверяющие элементы стрима на соответствие предикату.

  • anyMatch(predicate) — true, если хотя бы один элемент удовлетворяет условию
  • allMatch(predicate) — true, если ВСЕ элементы удовлетворяют условию
  • noneMatch(predicate) — true, если НИ ОДИН элемент не удовлетворяет условию
boolean hasAdults = users.stream().anyMatch(u -> u.getAge() >= 18);
boolean allActive = users.stream().allMatch(User::isActive);
boolean noBlocked = users.stream().noneMatch(User::isBlocked);

// Короткое замыкание:
// anyMatch — до первого true
// allMatch — до первого false
// noneMatch — до первого true
Что делают операции findFirst() и findAny()?

Краткий ответ: findFirst() возвращает Optional с первым элементом стрима (важен порядок). findAny() возвращает Optional с любым элементом (порядок не важен). В параллельном стриме findAny() быстрее, так как не требует координации между потоками.

Optional<User> first = users.stream()
    .filter(User::isAdmin)
    .findFirst();  // Первый админ

Optional<User> any = users.parallelStream()
    .filter(User::isAdmin)
    .findAny();    // Любой админ — в parallel быстрее, чем findFirst

Разница в параллельных стримах

  • findFirst() — требует сохранения порядка, медленнее в parallel
  • findAny() — порядок не важен, быстрее в parallel

🟣 Сборка в Map и Optional

Как собрать Stream в Map?

Краткий ответ: Использовать Collectors.toMap() с keyMapper и valueMapper. При возможности коллизий ключей — обязательно указывать mergeFunction.

// Простая сборка в Map
Map<Long, User> byId = users.stream()
    .collect(Collectors.toMap(User::getId, Function.identity()));

// С обработкой коллизий
Map<String, User> byEmail = users.stream()
    .collect(Collectors.toMap(
        User::getEmail,
        Function.identity(),
        (existing, replacement) -> replacement  // При дубликате: берём последнего
    ));

// С конкретной Map-реализацией
Map<Long, User> linkedMap = users.stream()
    .collect(Collectors.toMap(
        User::getId, u -> u, (a, b) -> a, LinkedHashMap::new
    ));

// Группировка
Map<String, List<User>> byDept = users.stream()
    .collect(Collectors.groupingBy(User::getDepartment));
Что делать при коллизиях ключей при сборке в Map?

Краткий ответ: По умолчанию toMap() бросает IllegalStateException при дубликатах ключей. Решение — явно указать mergeFunction (третий аргумент), которая определяет, какое значение оставить.

// Без merge — исключение при дубликатах
Map<String, User> bad = users.stream()
    .collect(Collectors.toMap(User::getEmail, Function.identity()));
// IllegalStateException: Duplicate key

// Стратегия 1: Оставить первое значение
(existing, replacement) -> existing

// Стратегия 2: Оставить последнее значение
(existing, replacement) -> replacement

// Стратегия 3: Суммировать
(existing, replacement) -> existing + replacement

// Стратегия 4: Выбрать по условию
(existing, replacement) -> 
    existing.createdAt().isAfter(replacement.createdAt()) ? existing : replacement

// Альтернатива: groupingBy сохраняет все значения
Map<String, List<User>> byEmail = users.stream()
    .collect(Collectors.groupingBy(User::getEmail));

Сравнение подходов

СценарийРешение
Уверен в уникальностиtoMap без merge
Оставить первое/последнееtoMap с merge (a,b) -> a / (a,b) -> b
Сохранить все значенияgroupingBy вместо toMap
Объединить значенияtoMap с merge-логикой
Как работать с Optional в Stream?

Краткий ответ: Для распаковки Optional в Stream используйте flatMap(Optional::stream) (JDK 9+). Для JDK 8 — filter(Optional::isPresent).map(Optional::get).

// JDK 9+: элегантная распаковка
List<Order> orders = users.stream()
    .map(User::getLastOrder)           // Stream<Optional<Order>>
    .flatMap(Optional::stream)         // Stream<Order>
    .collect(Collectors.toList());

// JDK 8: ручная распаковка
List<Order> orders = users.stream()
    .map(User::getLastOrder)
    .filter(Optional::isPresent)
    .map(Optional::get)
    .collect(Collectors.toList());

// findFirst/findAny возвращают Optional
Optional<User> first = users.stream()
    .filter(User::isAdmin)
    .findFirst();
String name = first.map(User::getName).orElse("No admin");

🟡 Продвинутые вопросы (Middle+)

Почему Stream ленивый и что это даёт?

Краткий ответ: Ленивость Stream означает, что промежуточные операции не выполняются до вызова терминальной. Это даёт оптимизацию (короткое замыкание), экономию памяти и однопроходность — все операции выполняются за один проход по данным.

Что даёт ленивость

  1. Короткое замыкание: limit(n) или findFirst() прекращают обработку досрочно
  2. Экономия памяти: не создаются промежуточные коллекции
  3. Однопроходность: filter + map + collect выполняется за один проход
  4. Оптимизация порядка операций: можно переставлять операции для эффективности
// Без ленивости: обработали бы ВСЕХ пользователей
// С ленивостью: обрабатываем только до нахождения 3 подходящих
List<String> result = users.stream()
    .filter(u -> expensiveCheck(u))  // Вызывается только для нужных
    .limit(3)                         // Останавливает обработку
    .collect(Collectors.toList());
Почему нельзя использовать Stream повторно?

Краткий ответ: Stream спроектирован как одноразовый конвейер. После вызова терминальной операции он считается потреблённым (consumed). Это связано с тем, что Stream может представлять собой не коллекцию в памяти, а поток данных (из файла, сети, генератор), который невозможно "перемотать".

Причины

  1. Однопроходность: многие источники (InputStream, генераторы) нельзя перечитать
  2. Ленивость: Stream не хранит данные — он их обрабатывает и передаёт дальше
  3. Оптимизация: отсутствие хранения позволяет не расходовать память
// Решение: Supplier для создания нового стрима
Supplier<Stream<String>> supplier = list::stream;
long count = supplier.get().count();
List<String> collected = supplier.get().collect(Collectors.toList());
Почему parallelStream() не всегда быстрее?

Краткий ответ: Parallel stream несёт накладные расходы на разбиение данных (splitting), координацию потоков, слияние результатов и использование общего ForkJoinPool. Для маленьких коллекций и простых операций эти расходы превышают выигрыш от параллелизма.

Факторы, замедляющие parallel stream

  • Оверхед на разбиение: разбиение коллекции на части и слияние результатов требуют ресурсов
  • Маленькие данные: для коллекций < 10K элементов оверхед перевешивает
  • Простые операции: если операция выполняется быстро, координация потоков дороже
  • Общий пул: другие задачи в commonPool() создают конкуренцию
  • Неделимые источники: например, Files.lines() плохо параллелится
  • Связанные данные: synchronized, общие переменные вызывают блокировки

Когда parallel stream ТОЧНО не поможет

  • I/O операции (диск, сеть — лучше CompletableFuture)
  • Операции с побочными эффектами
  • Операции, требующие порядка (sorted, findFirst)
Почему collect() безопаснее, чем forEach() с изменением внешней коллекции?

Краткий ответ: collect() не имеет побочных эффектов и безопасен в параллельных стримах — он использует локальные аккумуляторы и корректно их сливает. forEach() с изменением внешней коллекции создаёт побочный эффект, не потокобезопасен и нарушает контракт Stream API.

// ❌ Опасно: forEach с мутацией внешней коллекции
List<String> results = new ArrayList<>();
users.parallelStream()
    .filter(u -> u.getAge() > 18)
    .forEach(u -> results.add(u.getName()));  // Race condition!

// ✅ Безопасно: collect()
List<String> results = users.parallelStream()
    .filter(u -> u.getAge() > 18)
    .map(User::getName)
    .collect(Collectors.toList());  // Потокобезопасно даже в parallel

Почему collect() потокобезопасен

  1. Каждый поток создаёт свой локальный аккумулятор (supplier)
  2. Потоки независимо добавляют элементы в свои аккумуляторы
  3. При завершении аккумуляторы сливаются (combiner)
  4. Нет разделяемого изменяемого состояния
Чем groupingBy() отличается от partitioningBy()?

Краткий ответ: groupingBy() группирует элементы по произвольному ключу (любое количество групп). partitioningBy() разделяет элементы на две группы по булеву предикату (true/false). partitioningBy() — частный случай groupingBy(), более эффективный для бинарных классификаций.

КритерийgroupingBy()partitioningBy()
КлючЛюбой тип (Function<T, K>)Boolean (Predicate<T>)
Количество группЛюбоеВсегда 2 (true/false)
Результирующая MapMap<K, List<V>>Map<Boolean, List<V>>
Пустые группыНе создаютсяОбе создаются всегда
// groupingBy: группировка по отделу
Map<String, List<User>> byDept = users.stream()
    .collect(Collectors.groupingBy(User::getDepartment));

// partitioningBy: разделение на активных/неактивных
Map<Boolean, List<User>> byActive = users.stream()
    .collect(Collectors.partitioningBy(User::isActive));
// byActive.get(true) — активные
// byActive.get(false) — неактивные (всегда есть, даже если пусто)

Когда что использовать

  • partitioningBy() — когда нужны только две группы на основе условия (быстрее, всегда две группы)
  • groupingBy() — когда групп больше двух или ключ не boolean
