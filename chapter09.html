🔷 String Pool и создание строк

Как работает String Pool?

Краткий ответ: String Pool — это специализированный кеш строк в Heap, реализованный как хеш-таблица. Его задача — экономия памяти за счет переиспользования неизменяемых строковых литералов.

1. Литералы — compile-time разрешение

String a = "hello"; // объект в пуле
String b = "hello"; // ссылка на тот же объект
System.out.println(a == b); // true

2. Оператор new — принудительное создание объекта

String c = new String("hello"); // новый объект в куче (литерал уже в пуле)

3. Метод intern()

String s1 = new String("hello");        // 2 объекта
String s2 = s1.intern();                // 0 новых объектов
String s3 = "hello";                    // 0 новых объектов
System.out.println(s1 == s2);           // false
System.out.println(s2 == s3);           // true
Где хранится сама таблица String Pool?

Краткий ответ: Объекты String находятся в Java Heap. Структура StringTable (хеш-таблица со ссылками) находится в нативной памяти JVM (Native Memory).

Native Memory:
┌─────────────────┐
│  StringTable    │───> ссылки на объекты в Heap
└─────────────────┘
Java Heap:
┌─────────────────┐
│ String("Hello") │
│ String("World") │
└─────────────────┘
В чём разница между созданием String через литерал и через new?

Краткий ответ: Литерал берёт или создаёт объект в String Pool. new всегда создаёт новый объект в куче.

String a = "hello";            // 0 или 1 объект (из пула)
String b = new String("hello"); // минимум 1 объект (или 2, если литерала нет в пуле)
Когда стоит использовать intern()?

Краткий ответ: Точечно, когда много динамически создаваемых дублирующихся строк с длительным временем жизни. В большинстве случаев не нужен.

Когда ДА: парсинг CSV/JSON с повторяющимися полями, словари и справочники, дедупликация после десериализации.

Когда НЕТ: короткоживущие строки, уникальные строки (UUID, email), вместо G1 String Deduplication.

// Правильный паттерн — свой пул
Map<String, String> manualPool = new ConcurrentHashMap<>(1024);
String deduped = manualPool.putIfAbsent(s, s);
Почему String является иммутабельным?

Краткий ответ: Ради безопасности, производительности и корректности в многопоточной среде.

  • Безопасность: невозможность подмены параметров (Class.forName, пути к файлам, JDBC URL)
  • Многопоточность: immutable-объекты не требуют синхронизации
  • String Pool: иммутабельность — необходимое условие существования пула
  • Кеширование хеш-кода: поле hash вычисляется один раз
  • Ключи в Map: безопасное использование в HashMap

🔶 StringBuilder и StringBuffer

Когда использовать StringBuilder, а когда StringBuffer?

Краткий ответ: StringBuilder — всегда (99% случаев). StringBuffer — практически никогда, сохранён для обратной совместимости.

// StringBuffer — synchronized
public synchronized StringBuffer append(String str) { ... }

// StringBuilder — без синхронизации
public StringBuilder append(String str) { ... }
Почему StringBuffer медленнее StringBuilder?

Краткий ответ: Из-за накладных расходов на synchronized: захват монитора, барьеры памяти, запрет оптимизаций JIT.

ОперацияStringBuilderStringBuffer
1M append()~8 ms~12 ms (~50% медленнее)

🟢 Конкатенация строк

Что происходит при конкатенации строк через оператор +?

Краткий ответ: Компилятор преобразует + в цепочку StringBuilder.append(). Константы сворачиваются на этапе компиляции. В циклах += создаёт новый StringBuilder на каждой итерации (O(n²)).

// Константная свертка
String s = "Hello, " + "World!"; // становится "Hello, World!"

// Десахаринг в StringBuilder
String result = "User: " + name + ", age: " + age;
// → new StringBuilder().append("User: ").append(name).append(", age: ").append(age).toString()
Как компилятор Java оптимизирует конкатенацию строк?

Краткий ответ: Три уровня: константная свертка (compile-time), десахаринг в StringBuilder, а с JDK 9+ — invokedynamic с StringConcatFactory.

JEP 280 (JDK 9+): invokedynamic

// Байт-код JDK 9+
invokedynamic #0 <makeConcatWithConstants, BootstrapMethods #0>

Стратегии: MH_INLINE_SIZED_EXACT (самая быстрая, без StringBuilder), MH_SB_SIZED_EXACT, BC_SB (fallback).

🔵 Сравнение строк

Можно ли использовать == для сравнения String?

Краткий ответ: Можно только если обе строки гарантированно из одного пула (литералы или intern()). В 99% случаев — equals().

String a = "hello";          // пул
String b = "hello";          // пул
String c = new String("hello"); // куча
a == b   // true
a == c   // false
В чём разница между == и equals() для String?

Краткий ответ: == сравнивает ссылки (адреса в памяти), equals() сравнивает содержимое (последовательность символов).

Критерий==equals()
Что сравниваетСсылки (O(1))Содержимое (O(n))
null-безопасностьs == null работает"hello".equals(s) безопасно
Где хранится String Pool (в какой области памяти)?

Краткий ответ: С JDK 7 — в Heap. До JDK 7 — в PermGen.

JDK 6 и ранееJDK 7+
PermGen (фиксированный, строки не удалялись)Heap (сборка мусора, размер -Xmx)
Может ли String Pool вызвать OutOfMemoryError?

Краткий ответ: Да. До JDK 7 — OutOfMemoryError: PermGen space. С JDK 7+ — OutOfMemoryError: Java heap space.

Причина: String Pool — GC Root. Интернированные строки не удаляются, пока запись в StringTable существует.

🟣 Методы String

Что делает метод substring() и как он работал до Java 7?

Краткий ответ: До JDK 7 — разделял char[] с исходной строкой (O(1), но memory leak). С JDK 7 — копирует данные в новый массив (O(n), безопасно).

// JDK 6: утечка памяти
String huge = load100MBFile();
String tiny = huge.substring(0, 20); // tiny.value → 100 MB char[]!
huge = null; // массив не собран — tiny держит ссылку
Почему изменили реализацию substring() в Java 7?

Краткий ответ: Чтобы устранить скрытый memory leak. Маленькая подстрока удерживала огромный исходный char[].

GC не умеет собирать части примитивных массивов. Решение — копирование данных в новый массив.

Как работает метод split()?

Краткий ответ: Разбивает строку по регулярному выражению. Параметр limit управляет отбрасыванием пустых строк в конце.

"a,,b,c,,".split(",");     // ["a", "", "b", "c"] — limit=0, хвост отброшен
"a,,b,c,,".split(",", -1); // ["a", "", "b", "c", "", ""] — все сохранены
В чём особенность метода replace() vs replaceAll()?

Краткий ответ: replace() — литеральная замена. replaceAll() — регулярное выражение.

"a.b.c".replace(".", "/");    // "a/b/c" — точка это точка
"a.b.c".replaceAll(".", "/"); // "/////" — точка = любой символ!
"a.b.c".replaceAll("\\.", "/"); // "a/b/c" — правильное экранирование

🟡 Кодировки и преобразования

Что такое String encoding (кодировка)?

Краткий ответ: Кодировка — это набор правил, отображающих символы в числовые коды и обратно, а также определяющих, как эти числа представить в виде байтов. Критична при переходе String ↔ byte[].

Внутреннее устройство String (JDK 9+)

public final class String {
    private final byte[] value;  // LATIN-1 (1 байт) или UTF-16 (2/4 байта)
    private final byte coder;    // LATIN1 = 0, UTF16 = 1
}
Как правильно конвертировать String в byte[] и обратно?

Краткий ответ: Всегда явно указывайте StandardCharsets.UTF_8. Никогда не полагайтесь на методы без параметра charset.

// ✅ Правильно
byte[] bytes = str.getBytes(StandardCharsets.UTF_8);
String s = new String(bytes, StandardCharsets.UTF_8);

// ❌ Опасно: platform-dependent!
byte[] bytes = str.getBytes();  // Charset.defaultCharset()
String s = new String(bytes);   // Charset.defaultCharset()
Что такое compact strings в Java 9+?

Краткий ответ: JEP 254: замена char[] на byte[] + coder. LATIN-1 (1 байт/символ) для латиницы, UTF-16 для остальных. Экономия ~50% памяти на латинице.

"Hello"  → LATIN-1 (5 байт данных)
"Привет" → UTF-16  (12 байт данных)
Как узнать, сколько памяти занимает String?

Краткий ответ: Формула: ~40 + длина × (LATIN1 ? 1 : 2), округлить до кратного 8. Инструментально: JOL (GraphLayout.totalSize()) или heap dump.

"Hello"  → 40 + 5 = 45 → 48 байт (JDK 9+, LATIN-1)
"Привет" → 40 + 12 = 52 → 56 байт (JDK 9+, UTF-16)
Можно ли изменить содержимое String через рефлексию?

Краткий ответ: Технически да, но это опасно и ломает инварианты JVM. В JDK 17+ требует --add-opens.

// JDK 9+: изменение byte[] value через рефлексию
Field field = String.class.getDeclaredField("value");
field.setAccessible(true);
byte[] value = (byte[]) field.get(s);
value[0] = 'H'; // ломает пул, hashCode, потокобезопасность

🟠 Интерфейсы и оптимизации

Почему String implements Comparable и CharSequence?

Краткий ответ: Comparable — для естественного порядка сортировки. CharSequence — для полиморфной работы с последовательностями символов.

// Comparable: сортировка, TreeMap, binarySearch
Arrays.sort(names);

// CharSequence: единый API для String, StringBuilder, CharBuffer
void process(CharSequence cs) { ... }
Что такое String deduplication в G1 GC?

Краткий ответ: Механизм G1 GC, объединяющий внутренние массивы byte[] у разных String с одинаковым содержимым. Сами объекты String остаются разными (== не меняется).

String PoolString Deduplication
Объединяет объекты String (== true)Объединяет только byte[] (== false)
intern() / литералыАвтоматически при G1 GC
// Включение
-XX:+UseG1GC -XX:+UseStringDeduplication
