🔷 Основы исключений

В чём разница между checked и unchecked exceptions?

Короткий ответ: Checked exceptions проверяются компилятором — их обязательно обрабатывать (try-catch) или декларировать (throws). Unchecked exceptions — не проверяются компилятором, возникают на рантайме из-за ошибок программиста или состояния JVM. Первые наследуются от Exception (но не от RuntimeException), вторые — от RuntimeException и Error.

Иерархия (основа ответа)

Throwable
├── Error (unchecked)                     — проблемы JVM: OutOfMemoryError, StackOverflowError
└── Exception
    ├── RuntimeException (unchecked)      — ошибки программиста: NPE, IAE, IndexOutOfBounds
    └── Все остальные (checked)           — внешние условия: IOException, SQLException

Классы Error и RuntimeException и их потомки — unchecked. Все остальные потомки Exception — checked.

Checked exceptions

Суть: Отражают внешние, предсказуемые, но неконтролируемые программистом проблемы (сеть упала, файл удалили, БД недоступна). Компилятор принуждает разработчика осознанно принять решение: обработать исключение здесь и сейчас или пробросить выше.

Обязательная обработка:

// Код не скомпилируется без try-catch или throws
public String readFile(File file) {
    return Files.readString(file.toPath());  // Ошибка компиляции!
}

// Исправление -- вариант 1: throws в сигнатуре
public String readFile(File file) throws IOException {
    return Files.readString(file.toPath());
}

// Исправление -- вариант 2: try-catch
public String readFile(File file) {
    try {
        return Files.readString(file.toPath());
    } catch (IOException e) {
        throw new UncheckedIOException(e);  // Оборачиваем
    }
}

Примеры: IOException, SQLException, ClassNotFoundException, InterruptedException, FileNotFoundException.

Философия: Это часть публичного API метода. Глядя на throws IOException, вызывающий код понимает: "здесь я должен предусмотреть сценарий отказа".

Unchecked exceptions

Суть: Отражают ошибки в логике самой программы, которые можно предотвратить корректным кодом. Компилятор не заставляет их обрабатывать — предполагается, что разработчик напишет код правильно, и эти исключения не возникнут.

Не требуют обработки:

// Компилятор не требует try-catch, хотя NPE возможен
public String toUpper(String s) {
    return s.toUpperCase();  // Может быть NPE, но компилятор молчит
}

Примеры: NullPointerException, IllegalArgumentException, IndexOutOfBoundsException, ArithmeticException, ClassCastException.

Философия: Это баги, а не ожидаемые ситуации. Их не ловят — их исправляют в коде.

Error (тоже unchecked, но особый)

Проблемы уровня JVM, которые приложение не должно пытаться обработать:

// Так не делают
try {
    recursiveMethod();  // Бесконечная рекурсия
} catch (StackOverflowError e) {
    // JVM в нестабильном состоянии, бесполезно
}

OutOfMemoryError, StackOverflowError, NoClassDefFoundError — нет смысла ловить, JVM может быть повреждена.

Как выбирать между ними (для создания своих исключений)

Делайте checked, если: ошибка связана с внешним миром, вызывающий код может осмысленно восстановиться, вы хотите принудить разработчика задуматься об этом сценарии.

Делайте unchecked, если: ошибка вызвана некорректным использованием API, вызывающий код не может ничего исправить (это баг), это ошибка, которой "не должно случиться" при правильном использовании.

Проблема checked exceptions и современные подходы

Checked exceptions критикуют за захламление сигнатур методов, неудобство в лямбдах и Stream API, склонность разработчиков "проглатывать" исключения пустым catch.

Современный тренд (Spring, Lombok): бизнес-исключения делать unchecked, использовать @SneakyThrows для скрытой проброски checked, Spring транзакции откатываются только на unchecked по умолчанию.

Резюме для Middle+

Checked exceptions — механизм принуждения к обработке ожидаемых внешних сбоев через try-catch или throws. Unchecked — ошибки программирования и критические сбои JVM. Главное различие не в типах, а в философии: checked говорит "здесь возможен отказ, реши что делать", unchecked говорит "ты ошибся в коде, исправляй".

Что такое checked exception и когда его использовать?

Checked exception — это исключение, наследуемое от Exception (но не от RuntimeException), которое компилятор Java обязывает явно обрабатывать: либо через try-catch, либо декларируя в сигнатуре метода через throws. Его философия — отразить предсказуемую внештатную ситуацию, которая не является ошибкой программиста, и принудить вызывающий код осознанно решить, что с ней делать.

Механика: как компилятор принуждает

// Код не скомпилируется без throws или try-catch
public String readConfig(Path path) {
    return Files.readString(path);  // Ошибка компиляции: unreported exception IOException
}

// Вариант 1: throws -- перекладываю ответственность выше
public String readConfig(Path path) throws IOException {
    return Files.readString(path);
}

// Вариант 2: try-catch -- обрабатываю здесь и сейчас
public String readConfig(Path path) {
    try {
        return Files.readString(path);
    } catch (IOException e) {
        return DEFAULT_CONFIG;  // fallback
    }
}

Без одного из этих вариантов код не скомпилируется. Это главное отличие от unchecked исключений.

Философия: когда это уместно

Checked exception моделирует ситуацию, когда операция в принципе может не выполниться по причинам вне контроля программы, и вызывающий код способен осмысленно отреагировать. Три условия:

  1. Проблема не от программиста. Неправильные аргументы — это баг (unchecked). Недоступный файл — это реальность (checked).
  2. Вызывающий код МОЖЕТ восстановиться. Есть разумный сценарий кроме "упасть с ошибкой": повторить, использовать значение по умолчанию, уведомить пользователя, залогировать и продолжить.
  3. Вы ХОТИТЕ принудить к осознанию. Сигнатура метода — часть контракта. throws IOException громко заявляет: "Эй, здесь всё может пойти не так, подумай об этом сейчас, а не в продакшене".

Примеры из стандартной библиотеки

Files.readAllLines(path);                    // IOException
Class.forName("com.mysql.Driver");           // ClassNotFoundException
url.openConnection().getInputStream();       // IOException
Thread.sleep(1000);                          // InterruptedException

Когда НЕ использовать checked

Нарушение любого из трёх условий — сигнал делать unchecked.

// ПЛОХО: вызывающий код не может восстановиться -- это баг программиста
public void setAge(int age) throws InvalidAgeException {  // Должен быть unchecked!
    if (age < 0) throw new InvalidAgeException();
}

// ХОРОШО: unchecked для ошибок программиста
public void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("Age must be non-negative: " + age);
}

Реализация своего checked exception

public class PaymentGatewayException extends Exception {
    private final int errorCode;
    public PaymentGatewayException(String message, int errorCode, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
    }
    public int getErrorCode() { return errorCode; }
}

Проблема с лямбдами и Stream API

// Не компилируется: Files.readString бросает IOException
List<String> contents = fileList.stream()
    .map(Files::readString)
    .collect(Collectors.toList());

// Решение: обернуть в unchecked
List<String> contents = fileList.stream()
    .map(file -> {
        try { return Files.readString(file); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    })
    .collect(Collectors.toList());

Резюме для Middle+

Checked exception — это инструмент принуждения разработчика к осознанной обработке внештатных ситуаций. Он уместен, когда отказ вызван внешними причинами (не баг), вызывающий код способен восстановиться, и вы хотите сделать эту возможность явной частью контракта метода. Главное — не злоупотреблять: если вызывающий код не может ничего умного сделать с исключением, не надо заставлять его ловить — делайте unchecked.

Что такое unchecked exception (Runtime Exception)?

Unchecked exception — это исключение, наследующееся от RuntimeException (или Error), которое компилятор Java не заставляет обрабатывать. Его философия: отразить ошибку программиста или фатальный сбой JVM, которые нельзя предотвратить внешней обработкой — нужно исправлять код.

Иерархия

Throwable
├── Error (unchecked)                     — критические ошибки JVM
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── ...
└── Exception
    ├── RuntimeException (unchecked)      — ошибки программиста
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   ├── IndexOutOfBoundsException
    │   ├── ClassCastException
    │   └── ...
    └── Все остальные (checked)           — внешние условия

Почему компилятор молчит

// Компилируется без проблем — никаких try-catch или throws
public int sumLengths(String a, String b) {
    return a.length() + b.length();  // Может быть NPE, но компилятор не требует обработки
}

Компилятор предполагает: разработчик достаточно компетентен, чтобы не допускать таких ошибок. Null-проверка, валидация аргументов, проверка границ — это часть нормального кода, а не исключительные ситуации.

Три категории unchecked

1. Ошибки программиста (RuntimeException)

Возникают из-за багов в коде. Их не ловят — их предотвращают.

// NullPointerException — не проверили на null
public String greet(String name) {
    return "Hello, " + name.toUpperCase();  // NPE при name == null
}

// Исправление: проверка или Objects.requireNonNull
public String greet(String name) {
    Objects.requireNonNull(name, "name must not be null");
    return "Hello, " + name.toUpperCase();
}

// IllegalArgumentException — передали невалидный аргумент
public void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("Age must be non-negative: " + age);
}

// IndexOutOfBoundsException — вышли за границы
List<String> list = List.of("a", "b");
String third = list.get(2);  // IndexOutOfBoundsException — нужно было проверить size()

2. Критические ошибки JVM (Error)

Приложение не должно их обрабатывать — JVM в нестабильном состоянии.

// Бесконечная рекурсия
public void recurse() {
    recurse();  // StackOverflowError — не ловить!
}

// Утечка памяти
List<Object> list = new ArrayList<>();
while (true) list.add(new byte[1024 * 1024]);  // OutOfMemoryError

3. Пользовательские unchecked исключения

Когда хотите сообщить о нарушении контракта API:

public class InsufficientFundsException extends RuntimeException {
    private final BigDecimal balance;
    private final BigDecimal requested;
    public InsufficientFundsException(BigDecimal balance, BigDecimal requested) {
        super(String.format("Insufficient funds: balance=%s, requested=%s", balance, requested));
        this.balance = balance;
        this.requested = requested;
    }
}

Когда ловить unchecked (редкие случаи)

В общем случае unchecked не ловят. Но есть осмысленные исключения: защита потока от падения, очистка ресурсов, оборачивание checked в unchecked для совместимости, глобальный обработчик (последний рубеж).

Резюме для Middle+

Unchecked exceptions (RuntimeException и Error) — это исключения, не требующие принудительной обработки компилятором. Они сигнализируют об ошибках программиста или фатальных сбоях JVM. Их философия: "это не должно происходить, а если происходит — код нужно чинить, а не ловить". Практическое правило: если вызывающий код может предотвратить исключение проверкой предусловий — делайте unchecked.

Какие исключения нужно обрабатывать обязательно?

Обязательно нужно обрабатывать только checked exceptions — те, которые наследуются от Exception, но не от RuntimeException. Компилятор Java физически не даст запустить код, пока вы либо не обернёте такой вызов в try-catch, либо не добавите throws в сигнатуру метода. Unchecked exceptions (RuntimeException и Error) обрабатывать не обязательно.

Три варианта обязательной обработки

// Метод, бросающий checked exception
public String readFile(Path path) throws IOException {
    return Files.readString(path);
}

// Вариант 1: try-catch — ловим здесь и сейчас
public String loadConfig() {
    try {
        return readFile(Path.of("config.json"));
    } catch (IOException e) {
        System.err.println("Config not found, using defaults");
        return DEFAULT_CONFIG;
    }
}

// Вариант 2: throws — пробрасываем выше
public String loadConfig() throws IOException {
    return readFile(Path.of("config.json"));
}

// Вариант 3: Оборачиваем в unchecked
public String loadConfig() {
    try {
        return readFile(Path.of("config.json"));
    } catch (IOException e) {
        throw new UncheckedIOException("Failed to load config", e);
    }
}

Unchecked exceptions — обрабатывать не обязательно

// Компилируется без проблем
public int divide(int a, int b) {
    return a / b;  // ArithmeticException при b=0 — компилятор молчит
}

public String getFirst(List<String> list) {
    return list.get(0);  // IndexOutOfBoundsException при пустом списке
}

Практическое правило: что ДЕЙСТВИТЕЛЬНО нужно обрабатывать

Формально обязательны — checked. Но на практике хороший код обрабатывает и некоторые unchecked в определённых точках: глобальный обработчик (ControllerAdvice), защита цикла, в транзакции (откат на любое исключение).

Что находится в вершине иерархии исключений?

В вершине иерархии находится Throwable. Все классы исключений и ошибок в Java происходят от этого единого корня. Ключевой момент для собеседования — умение правильно нарисовать и объяснить раздвоение этой иерархии на Exception и Error.

Полная иерархия

Object
└── Throwable                     ← ВЕРШИНА (корень)
    ├── Error                     ← Ошибки JVM (unchecked)
    │   ├── OutOfMemoryError
    │   ├── StackOverflowError
    │   └── ...
    └── Exception                 ← Исключения приложения
        ├── RuntimeException     ← Ошибки программиста (unchecked)
        │   ├── NullPointerException
        │   ├── IllegalArgumentException
        │   └── ...
        └── (все остальные)       ← Внешние условия (checked)
            ├── IOException
            ├── SQLException
            └── ...

Что важно сказать о Throwable

1. Основные члены класса: детальное сообщение (detailMessage), причина (cause), трассировка стека (stack trace).

2. Конструкторы и подавленные исключения: в Java 7 появились подавленные исключения (suppressed). Они добавляются через метод addSuppressed(Throwable). Основной кейс — try-with-resources: если мы сломались при закрытии ресурса, это исключение не должно затирать основную ошибку.

3. Главный антипаттерн: никогда нельзя писать catch (Throwable t). Это перехватит не только программные ошибки, но и Error'ы, после которых JVM может находиться в нестабильном состоянии.

Что такое Throwable?

Throwable — это корневой класс всей иерархии ошибок и исключений в Java. Он является единственным типом, который можно "бросить" через throw и "поймать" через catch. Это не интерфейс и не просто удобная абстракция, а полноценный класс, наследующий Object.

1. Роль в JVM: контракт throw/catch

// ЗАКОН JVM: после throw может стоять ТОЛЬКО объект Throwable или его наследник.
throw new Throwable();       // ОК
throw new Exception();       // ОК (наследник)
throw new RuntimeException(); // ОК (наследник)
throw new String("error");   // Ошибка компиляции! String не наследник Throwable

2. Внутреннее устройство

public class Throwable implements Serializable {
    private String detailMessage;         // Сообщение
    private Throwable cause;              // Первопричина
    private StackTraceElement[] stackTrace; // Стек вызовов
    private List<Throwable> suppressedExceptions; // Подавленные исключения
}

Четыре столпа Throwable:

  1. Stack Trace — заполняется в момент создания вызовом fillInStackTrace(). Именно поэтому создание исключений — относительно дорогая операция.
  2. Cause — реализует паттерн "цепочка исключений". Позволяет сохранить первопричину, обернув её в исключение более высокого уровня.
  3. Suppressed — главное новшество Java 7 (try-with-resources). Если основная логика упала, а при закрытии ресурса тоже возникла ошибка — она не замещает основную, а добавляется в suppressed.
  4. Геттеры и иммутабельность — getMessage(), getCause(), getStackTrace() без сеттеров.

3. Как работает throw

throw new Throwable() создает объект и заполняет стек. JVM начинает раскручивать стек вызовов в поисках подходящего catch. Если catch не найден — поток умирает. Если finally встречается по пути — он обязательно выполняется.

4. Антипаттерны

Никогда не ловите Throwable без крайней нужды. Не создавайте исключения без надобности (new Exception() ради стектрейса — дорого).

Резюме для Middle+

Throwable — это не просто "родитель", а единственный легальный тип для системы throw/catch в JVM. Он реализует три критических механизма: снимок стека, цепочку причин и подавление исключений. Понимание того, что стек сохраняется в момент new, а не в момент throw, и чем грозит catch (Throwable t) — граница между Junior'ом и Middle'ом в теме исключений.

В чём разница между Error и Exception?

Короткий ответ: Error — это критические проблемы уровня JVM или железа, которые приложение не должно пытаться обрабатывать (нет смысла, JVM нестабильна). Exception — это проблемы уровня приложения, которые можно и нужно обрабатывать, они делятся на checked и unchecked.

1. Разница по уровням ответственности

Throwable
├── Error                     ← Зона ответственности JVM (железо, память, байт-код)
│   ├── OutOfMemoryError      — закончилась куча, GC не помог
│   ├── StackOverflowError    — бесконечная рекурсия
│   ├── NoClassDefFoundError  — класс был при компиляции, но отсутствует в runtime
│   ├── AssertionError        — сработал assert
│   └── ...
└── Exception                 ← Зона ответственности приложения
    ├── RuntimeException      — баги в коде (unchecked)
    └── IOException           — внешние условия (checked)

Мнемоника: Error — "всё пропало, JVM умирает". Exception — "что-то пошло не так, но можно исправить".

2. Ключевые различия

// КАТАСТРОФИЧЕСКИ ПЛОХОЙ КОД — никогда так не делайте!
public void dangerous() {
    try {
        recursiveOverflow();

4. Как объяснить на собеседовании за 30 секунд

"Error — это проблемы JVM: кончилась память, стек переполнен, сломанный байт-код. Их бессмысленно ловить, потому что среда выполнения нестабильна. Exception — это проблемы приложения: сеть упала, файл не найден, передан null. Их нужно обрабатывать, потому что приложение может восстановиться."

🔶 Try-Catch-Finally и Try-With-Resources

Гарантируется ли выполнение блока finally?

Короткий ответ: Нет, не гарантируется. Блок finally выполняется почти всегда, но существуют конкретные сценарии, когда JVM до него просто "не доживает".

1. Когда finally выполняется (обычные сценарии)

try {
    System.out.println("try");
    return; // Даже тут finally отработает
} finally {
    System.out.println("finally"); // Выполнится перед return!
}

2. Ситуации, когда finally НЕ выполняется

Ситуация 1: System.exit()

try {
    System.out.println("try");
    System.exit(0); // Принудительное завершение JVM
} finally {
    System.out.println("finally"); // ЭТО НЕ ВЫПОЛНИТСЯ
}

Ситуация 2: Аварийное падение JVM (Error уровня краша) — может не выполниться.

Ситуация 3: kill -9 (SIGKILL) из ОС — мгновенное уничтожение процесса.

Ситуация 4: Бесконечный цикл или дедлок в try/catch — никогда не выйдем из try.

Ситуация 5: Отключение питания / крах ОС — аппаратный сбой.

3. Как отвечать на собеседовании

"Блок finally выполняется почти всегда, если поток выполнения доходит до try. Он сработает даже при return или исключении. Однако есть исключения: System.exit(), аварийное завершение JVM, kill -9 из ОС, бесконечный цикл в try. Поэтому 100% гарантии нет — полагаться на finally для критически важных действий, которые должны пережить крах JVM, нельзя."

Что такое try-with-resources?

try-with-resources — это конструкция Java (появилась в JDK 7), которая автоматически закрывает ресурсы, объявленные в заголовке try, сразу после выхода из блока — будь то нормальное завершение, return или исключение. Ключевой интерфейс — AutoCloseable.

1. Как это выглядит

// Старый подход (Java 6-): finally и ручное закрытие
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("file.txt"));
    String line = br.readLine();
} catch (IOException e) { ... }
finally {
    if (br != null) {
        try { br.close(); } catch (IOException e) { }
    }
}

// try-with-resources (Java 7+): компактно и безопасно
try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
    String line = br.readLine();
} catch (IOException e) { ... }
// br.close() вызван автоматически

2. Механика работы

Шаг 1. Ресурсы должны реализовывать AutoCloseable. Closeable наследует AutoCloseable, уточняя сигнатуру до throws IOException.

Шаг 2. Порядок закрытия: ресурсы закрываются в порядке, обратном их объявлению (LIFO — последний открытый закрывается первым).

Шаг 3. Подавленные исключения (suppressed): если основной код выбросил исключение, а при закрытии ресурса тоже произошло исключение — второе не заменяет основное, а добавляется как подавленное.

3. Эволюция: JDK 7 → JDK 9

// JDK 7-8: обязательно объявление в try()
try (BufferedReader br = new BufferedReader(...)) { ... }

// JDK 9+: можно использовать effectively final переменные
BufferedReader br = new BufferedReader(...);
try (br) { ... }  // br должен быть effectively final

4. Когда использовать

Всегда, когда ресурс реализует AutoCloseable: IO-потоки, JDBC-соединения, сетевые сокеты, любые свои классы, инкапсулирующие нативные ресурсы.

5. Как написать свой AutoCloseable

public class DatabaseConnection implements AutoCloseable {
    private boolean closed = false;
    public void executeQuery(String sql) {
        if (closed) throw new IllegalStateException("Connection is closed");
    }
    @Override
    public void close() {
        if (!closed) { closed = true; /* освобождение ресурсов */ }
    }
}

Резюме для Middle+

try-with-resources — это синтаксический сахар над finally для автоматического управления ресурсами. Ресурсы должны реализовывать AutoCloseable, закрываются в обратном порядке объявления (LIFO), а исключения при закрытии не маскируют основную ошибку, а добавляются как suppressed. С JDK 9 можно использовать внешние effectively final переменные.

Чем try-with-resources лучше ручного finally и почему LIFO?

Почему try-with-resources лучше ручного finally

1. Проблема потерянного исключения (главная причина)

Ручной finally маскирует основную ошибку. Если в try возникло исключение, а в finally при закрытии ресурса тоже — исключение из finally перезаписывает основное:

// Ручной finally — основная ошибка теряется
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("file.txt"));
    throw new IOException("Ошибка чтения"); // ОСНОВНАЯ ошибка
} finally {
    if (br != null) {
        br.close(); // Здесь тоже IOException ("Ошибка закрытия")
    }
}
// До разработчика долетит только "Ошибка закрытия"
// Истинная причина "Ошибка чтения" потеряна навсегда

try-with-resources решает эту проблему через механизм подавленных исключений: основная ошибка из try остаётся главной, ошибка закрытия добавляется в getSuppressed().

2. Пропуск закрытия ресурса. В ручном finally легко забыть проверить на null или перепутать порядок.

3. Многословность. 3 ресурса = ~25 строк шаблонного кода против 1 строки объявления.

Почему закрытие в обратном порядке (LIFO)

Аналогия: вы надеваете пальто поверх пиджака. Снимаете сначала пальто, потом пиджак.

Техническая причина — зависимость ресурсов:

Connection conn = DriverManager.getConnection(url);       // 1. Открыто первым
PreparedStatement stmt = conn.prepareStatement(sql);      // 2. Зависит от conn
ResultSet rs = stmt.executeQuery();                       // 3. Зависит от stmt

// Прямой порядок (НЕПРАВИЛЬНО):
conn.close();  // Закрыли соединение
stmt.close();  // Поздно! Statement ссылается на мёртвое соединение
rs.close();    // Поздно!

// Обратный порядок LIFO (ПРАВИЛЬНО):
rs.close();    // 3. Закрыли первым
stmt.close();  // 2. Statement больше не нужен
conn.close();  // 1. Соединение закрыто последним

LIFO гарантирует: ресурс жив, пока живы все, кто на него ссылается. Когда close() вызывается на родительском ресурсе, все дочерние уже корректно освобождены.

Резюме для собеседования

Чем лучше: сохраняет основное исключение (suppressed), гарантирует закрытие всех ресурсов, убирает шаблонный код. Почему LIFO: ресурсы часто зависят друг от друга, закрытие родительского при живых дочерних вызывает ошибки, обратный порядок гарантирует корректное освобождение.

Какие требования к ресурсам в try-with-resources?

Короткий ответ: Ресурс, объявленный в try-with-resources, должен реализовывать интерфейс java.lang.AutoCloseable (или его подтип java.io.Closeable). Это единственное жёсткое требование компилятора.

1. Интерфейс AutoCloseable

public interface AutoCloseable {
    void close() throws Exception;  // Может бросать любое исключение
}
// Closeable наследует AutoCloseable с уточнённой сигнатурой:
public interface Closeable extends AutoCloseable {
    void close() throws IOException;  // Только IOException
}

2. Что считается ресурсом (эволюция JDK)

// JDK 7-8: ресурс должен быть объявлен внутри try
try (BufferedReader br = new BufferedReader(...)) { }

// JDK 9+: допускаются effectively final переменные
BufferedReader br = new BufferedReader(...);
try (br) { }  // Компилируется с JDK 9+

3. Свой AutoCloseable: минимальная реализация

public class ManagedResource implements AutoCloseable {
    private boolean closed = false;
    public void doWork() {
        if (closed) throw new IllegalStateException("Resource closed");
        System.out.println("Working...");
    }
    @Override
    public void close() {
        if (!closed) {
            closed = true;
            System.out.println("Resource released");
        }
        // Важно: close() должен быть идемпотентным!
    }
}

4. Требования к реализации close()

Идемпотентностьclose() может вызываться повторно

ПотокобезопасностьЕсли ресурс используется из нескольких потоков

5. Распространённые ошибки

Ресурс без AutoCloseable — ошибка компиляции. Изменение effectively final переменной в JDK 9+ — ошибка компиляции. close() не идемпотентен — баг.

6. Несколько ресурсов

Можно объявлять несколько ресурсов через ; (не ,!). Закрываются в обратном порядке (LIFO: rs → stmt → conn).

Что такое AutoCloseable интерфейс?

AutoCloseable — это интерфейс из java.lang, появившийся в JDK 7. Содержит единственный метод void close() throws Exception и является фундаментом для конструкции try-with-resources. Любой класс, реализующий этот интерфейс, может быть использован как ресурс, автоматически закрываемый JVM.

1. Определение и контракт

package java.lang;
public interface AutoCloseable {
    void close() throws Exception;
}

Метод вызывается автоматически при выходе из try-with-resources, может бросать Exception, рекомендуется делать идемпотентным.

2. Место в иерархии

AutoCloseable (java.lang, JDK 7)
    ↑
Closeable (java.io, JDK 1.5 — но с JDK 7 наследует AutoCloseable)
    void close() throws IOException;

3. Кто его реализует

IO-потоки (InputStream, OutputStream, Reader, Writer), JDBC (Connection, Statement, ResultSet), сеть (Socket, ServerSocket), Concurrency (ExecutorService), файловые системы (FileSystem, FileChannel).

4. Свой класс: пример

public class ManagedResource implements AutoCloseable {
    private boolean closed = false;
    public void doWork() {
        if (closed) throw new IllegalStateException("Already closed");
        System.out.println("Working...");
    }
    @Override
    public void close() {
        if (!closed) {
            closed = true;
            System.out.println("Cleaned up");
        }
    }
}

В чём разница между AutoCloseable и Closeable?

Короткий ответ: AutoCloseable — это общий интерфейс из java.lang (JDK 7) для любых ресурсов с методом void close() throws Exception. Closeable — это его подтип из java.io (JDK 5, обновлён в JDK 7) для IO-ресурсов с уточнённой сигнатурой void close() throws IOException. Closeable наследует AutoCloseable, сужая тип исключения.

1. Иерархия и сигнатуры

// java.lang — JDK 7
public interface AutoCloseable {
    void close() throws Exception;
}

// java.io — JDK 5, обновлён в JDK 7
public interface Closeable extends AutoCloseable {
    @Override
    void close() throws IOException;  // Суженная сигнатура
}

3. Почему Closeable сужает throws до IOException

IO-операции бросают IOException и его подклассы. Closeable гарантирует: если вы закрываете IO-поток, вы будете иметь дело только с IOException, а не с абстрактным Exception.

4. Когда что использовать

Реализуйте Closeable, если: ресурс связан с вводом-выводом, естественное исключение при закрытии — IOException, хотите вписаться в экосистему IO.

Реализуйте AutoCloseable, если: ресурс не связан с IO (пул соединений, distributed lock), при закрытии могут возникнуть исключения не IOException, создаёте универсальный API.

5. Исторический контекст

До JDK 7 существовал только Closeable в java.io. Когда ввели try-with-resources, потребовался универсальный интерфейс. Создали AutoCloseable в java.lang, а Closeable ретрофитнули — сделали его подтипом. Это сохранило обратную совместимость.

🟢 Обработка исключений

Можно ли несколько catch блоков для одного try?

Короткий ответ: Да. Один try может иметь несколько catch блоков. Это фундаментальная возможность Java для дифференцированной обработки разных типов исключений. С JDK 7 также доступен multi-catch — перехват нескольких типов исключений в одном catch блоке через синтаксис с вертикальной чертой.

1. Несколько catch блоков — базовая механика

try {
    Files.readAllLines(Path.of("config.txt"));
    int port = Integer.parseInt(System.getProperty("port"));
    ServerSocket socket = new ServerSocket(port);
} catch (FileNotFoundException e) {
    System.err.println("Config file not found: " + e.getMessage());
    loadDefaultConfig();
} catch (NumberFormatException e) {
    System.err.println("Invalid port number");
    System.exit(1);
} catch (IOException e) {
    System.err.println("IO error: " + e.getMessage());
    logger.error("Server startup failed", e);
    throw new ServiceException("Cannot start server", e);
}

Ключевые правила:

  • Catch блоки проверяются сверху вниз
  • Первый подходящий по типу — выполняется
  • Остальные игнорируются
  • Порядок критичен: от частного к общему

2. Порядок catch блоков: от частного к общему

// ПРАВИЛЬНО: FileNotFoundException → IOException
try {
    Files.readAllLines(Path.of("file.txt"));
} catch (FileNotFoundException e) { ... }
catch (IOException e) { ... }

// ОШИБКА КОМПИЛЯЦИИ: общее перед частным
try {
    Files.readAllLines(Path.of("file.txt"));
} catch (IOException e) { ... }
catch (FileNotFoundException e) { ... }  // Ошибка: unreachable catch block

3. Multi-catch (JDK 7+)

try {
    process();
} catch (IOException | SQLException e) {
    logger.error("Operation failed", e);
    throw new ServiceException(e);
}

Ограничения: типы не должны быть в иерархии, переменная e неявно final.

4. Исключения, которые не стоит ловить вместе

Слишком широкий catch (Exception e) маскирует ошибки программирования. Error ловить опасно. Try + finally без catch — легально.

Что такое multi-catch (catching multiple exceptions)?

Multi-catch — это синтаксическая конструкция JDK 7, позволяющая перехватывать несколько типов исключений в одном блоке catch через разделитель |. Устраняет дублирование кода, когда разные исключения обрабатываются одинаково. Переменная исключения в таком блоке неявно final.

1. Синтаксис и базовая механика

// До JDK 7: дублирование обработчиков
try {
    process();
} catch (IOException e) {
    logger.error("Operation failed", e);
    throw new ServiceException(e);
} catch (SQLException e) {
    logger.error("Operation failed", e);
    throw new ServiceException(e);
}

// JDK 7+: multi-catch — один блок
try {
    process();
} catch (IOException | SQLException e) {
    logger.error("Operation failed", e);
    throw new ServiceException(e);
}

2. Технические ограничения

Типы не должны состоять в иерархии наследования:

// Ошибка компиляции: FileNotFoundException — подкласс IOException
catch (FileNotFoundException | IOException e) { }  // Ошибка!

Переменная исключения неявно final:

catch (IOException | SQLException e) {
    e = new IOException();  // Ошибка компиляции!
}

Нельзя выбрасывать объединённый тип без соответствующего throws в сигнатуре.

3. Как это выглядит в байт-коде

Создаётся общий catch для Throwable с проверкой instanceof внутри. HotSpot JVM оптимизирует это лучше, чем ручные проверки instanceof.

4. Практические применения

Единая точка логирования и оборачивания, fallback-логика при недоступности внешних сервисов, очистка ресурсов при разных ошибках.

5. Когда НЕ использовать

Если обработка различается — разные catch. Если нужно знать конкретный тип внутри блока — лучше разделить.

В каком порядке располагать catch блоки?

Короткий ответ: От наиболее частного (специфичного) к наиболее общему. Сначала подклассы, потом суперклассы. Нарушение этого порядка вызывает ошибку компиляции "unreachable catch block".

1. Железное правило: от частного к общему

// ПРАВИЛЬНО
try { readFile(); }
catch (FileNotFoundException e) { ... }       // Самый конкретный
catch (EOFException e) { ... }                 // Тоже конкретный
catch (IOException e) { ... }                  // Общий
catch (RuntimeException e) { ... }             // Ещё более общий

// НЕПРАВИЛЬНО — ошибка компиляции
try { readFile(); }
catch (IOException e) { ... }                  // Перехватит всё
catch (FileNotFoundException e) { ... }        // Ошибка: unreachable!

2. Почему это ошибка компиляции

Java гарантирует, что каждый reachable catch блок может быть выполнен. Если общий тип стоит перед частным, компилятор статически доказывает, что до частного блока управление никогда не дойдёт.

3. Полная иерархия для запоминания

Throwable
├── Error                          ← Не ловить без крайней необходимости
└── Exception
    ├── IOException                ← Checked
    │   ├── FileNotFoundException
    │   ├── EOFException
    │   └── SocketException
    ├── SQLException               ← Checked
    └── RuntimeException           ← Unchecked
        ├── NullPointerException
        ├── IllegalArgumentException
        └── IndexOutOfBoundsException

4. Multi-catch и порядок

Multi-catch блок можно размещать наравне с обычными catch блоками, соблюдая то же правило.

5. Стратегия: когда ловить частное, а когда общее

Разная реакция на разные типы — отдельные catch. Одинаковая реакция — общий catch или multi-catch. Выбор определяется бизнес-логикой восстановления, а не типом исключения.

6. Мнемоническое правило

"Дети перед родителями". Подклассы всегда перед суперклассами. Или: "От специального к общему".

Можно ли повторно бросить исключение?

Короткий ответ: Да. Повторно бросить исключение можно тремя способами: пробросить исходное как есть (throw e), обернуть в новое с сохранением причины (throw new WrapperException(e)), или использовать fillInStackTrace() для сброса стек-трейса.

1. Простой проброс: throw e без изменений

public void processFile(String path) throws IOException {
    try {
        Files.readAllLines(Path.of(path));
    } catch (IOException e) {
        logger.error("Failed to read file: {}", path, e);
        throw e;  // Пробрасываем то же исключение
    }
}

Исходный стек-трейс полностью сохраняется. Используется для логирования без изменения семантики ошибки.

2. Обёртывание в новое исключение с сохранением причины

public User loadUser(Long id) throws ServiceException {
    try {
        return database.query("SELECT * FROM users WHERE id = ?", id);
    } catch (SQLException e) {
        throw new ServiceException("Failed to load user " + id, e);
    }
}

Создаётся новое исключение более высокого уровня абстракции. Исходное SQLException сохраняется как cause.

3. Сброс стек-трейса: fillInStackTrace()

throw (RuntimeException) e.fillInStackTrace();

Применяется для сокрытия внутренней структуры системы. Теряется информация о реальной причине ошибки.

4. Проброс без объявления throws (sneaky throw)

Checked-исключение пробрасывается без объявления в сигнатуре. Технически возможно, но нарушает контракт метода.

5. Частая ошибка: потеря причины

// ПЛОХО: причина потеряна
throw new ServiceException("Query failed");  // SQLException потерян!

// ХОРОШО: причина сохранена
throw new ServiceException("Query failed", e);  // e — cause

Резюме для Middle+

Ключевые правила: простой throw e для прозрачного проброса; throw new WrapperException(msg, e) для перехода между уровнями абстракции с обязательным сохранением cause; fillInStackTrace() только для сокрытия внутренней структуры. Никогда не терять исходное исключение при обёртывании.

Что такое exception chaining?

Exception chaining — это механизм связывания исключений в причинно-следственную цепь, где одно исключение является причиной другого. Реализуется через конструкторы с параметром cause и метод getCause().

1. Как это работает

// Низкоуровневая операция
public User findUser(Long id) throws SQLException {
    return database.query("SELECT * FROM users WHERE id = ?", id);
}

// Высокоуровневая операция — оборачиваем с сохранением причины
public UserProfile getUserProfile(Long userId) throws ProfileException {
    try {
        User user = findUser(userId);
        return buildProfile(user);
    } catch (SQLException e) {
        throw new ProfileException("Failed to load profile for user " + userId, e);
    }
}

2. API для создания цепочки

// Конструкторы с причиной
public Throwable(String message, Throwable cause);
public Throwable(Throwable cause);

// Методы
public Throwable getCause();
public Throwable initCause(Throwable);   // Только один раз

3. Как выглядит стек-трейс с цепочкой

ProfileException: Failed to load profile for user 42
    at UserService.getUserProfile(UserService.java:25)
Caused by: java.sql.SQLException: Connection refused
    at Database.query(Database.java:42)

5. Типичные ошибки

Потеря причины при обёртывании, обёртывание без добавления контекста, разрыв цепочки при логировании.

🔵 Проброс и логирование

Что делает ключевое слово throws?

throws в сигнатуре метода декларирует проверяемые исключения (checked exceptions), которые метод может выбросить, но не обрабатывает сам. Это часть контракта метода: вызывающий код обязан либо перехватить эти исключения через try-catch, либо пробросить дальше по цепочке.

1. Синтаксис и базовое поведение

public void readFile(String path) throws IOException, FileNotFoundException {
    Files.readAllLines(Path.of(path));
    // Вызывающий код должен их обработать
}

На вызывающей стороне — обязательная реакция:

// Вариант 1: try-catch
try { readFile("config.txt"); }
catch (IOException e) { ... }

// Вариант 2: пробросить дальше
public void init() throws IOException {
    readFile("config.txt");
}

2. Полиморфизм и ограничения

При переопределении метода НЕЛЬЗЯ расширять список проверяемых исключений. Можно сужать или убирать.

3. Главная критика checked exceptions

Современная Java-экосистема отходит от checked exceptions: конфликт с лямбдами и Stream API, захламление сигнатур, Spring транзакции по умолчанию откатывают только на unchecked.

Можно ли пробросить checked exception из метода без throws?

Да, технически можно — через трюк с дженериками (sneaky throw), который обманывает компилятор. JVM не различает checked и unchecked исключения. Проверка происходит только в javac.

1. Классический sneaky throw

public class SneakyThrow {
    @SuppressWarnings("unchecked")
    private static <E extends Throwable> void sneakyThrow(Throwable e) throws E {
        throw (E) e;
    }
    
    public static void main(String[] args) {
        sneakyThrow(new IOException("Checked exception sneaked out!"));
    }
}

2. Как это работает

  1. sneakyThrow параметризован <E extends Throwable> и объявляет throws E
  2. При вызове компилятор выводит E как RuntimeException
  3. throws RuntimeException не требует обработки — компилятор доволен
  4. В рантайме дженерики стираются и выбрасывается настоящий IOException

3. Lombok @SneakyThrows

@SneakyThrows
public String readFile(String path) {
    return Files.readString(Path.of(path)); // IOException без throws!
}

4. Риски

Нарушение контракта метода, сломанная обработка исключений, несовместимость с полиморфизмом, усложнение отладки.

5. Когда допустимо

Утилиты функционального программирования (jOOL, Vavr), локальные хелперы внутри одного класса. Никогда в публичном API.

Что произойдёт, если в блоке finally тоже возникнет исключение?

Исходное исключение теряется. Если исключение возникает в finally, оно заменяет исходное исключение из try или catch. Это одна из самых коварных ловушек в Java.

1. Классический сценарий

public void readAndClose() throws IOException {
    InputStream is = null;
    try {
        is = new FileInputStream("data.bin");
        int data = is.read();  // IOException A
    } finally {
        if (is != null) {
            is.close(); // IOException B — перезаписывает A!
        }
    }
}

2. Детальная механика

try {
    throw new SQLException("Connection lost"); // Исключение 1
} finally {
    throw new RuntimeException("Finally failed"); // Исключение 2
}
// Стек-трейс покажет RuntimeException, SQLException исчезло

3. Try-with-resources — решение проблемы

try (InputStream is = new FileInputStream("data.bin")) {
    is.read();  // IOException A — основное
} // close() бросает IOException B — SUPPRESSED
// A.getSuppressed() содержит B

4. Возврат значения из finally — ещё одна ловушка

public int test() {
    try {
        return 10 / 0; // ArithmeticException
    } finally {
        return 42; // Перезаписывает исключение!
    }
}
// Вернёт 42 без исключений!
Что такое suppressed exceptions?

Suppressed exceptions — это механизм JDK 7, позволяющий сохранить информацию о вторичных исключениях, возникших при закрытии ресурсов. Вторичные исключения присоединяются к основному через addSuppressed() и доступны через getSuppressed().

1. Проблема, которую решают

До JDK 7 закрытие ресурсов в finally приводило к катастрофической потере информации — исключение закрытия перезаписывало основную ошибку.

2. Как это работает: try-with-resources

try (InputStream is = new FileInputStream("data.bin")) {
    is.read();  // IOException A — основное
} // close() бросает IOException B — подавленное
// IOException A.getSuppressed() содержит IOException B

3. API

public class Throwable {
    public final void addSuppressed(Throwable exception);
    public final Throwable[] getSuppressed();
}

4. Несколько ресурсов — несколько suppressed

Ресурсы закрываются в обратном порядке (LIFO). getSuppressed()[0] — исключение из последнего открытого ресурса.

5. Отличие от cause

Параллельные ошибкиПричинно-следственная связь

🟣 Проектирование исключений

Можно ли создавать кастомные исключения?

Да, и это стандартная практика. Механизм прост: наследуетесь от одного из классов иерархии Throwable. Ключевой момент — правильный выбор родителя (checked или unchecked) и реализация конструкторов для сохранения цепочки причин.

1. Базовая структура (4 конструктора — золотой стандарт)

public class PaymentFailedException extends RuntimeException {
    private final int errorCode;

    public PaymentFailedException(String message) { super(message); }
    public PaymentFailedException(String message, Throwable cause) { super(message, cause); }
    public PaymentFailedException(Throwable cause) { super(cause); }
    public PaymentFailedException(String message, Throwable cause,
                                   boolean enableSuppression, boolean writableStackTrace) {
        super(message, cause, enableSuppression, writableStackTrace);
    }
    public int getErrorCode() { return errorCode; }
}

2. Checked или Unchecked?

Checked (extends Exception): сбой ожидаем из-за внешнего мира, клиент может восстановиться.

Unchecked (extends RuntimeException): ошибка программиста, нарушение контракта API.

Современный тренд: unchecked для бизнес-логики.

3. Тонкости и антипаттерны

Не изобретайте велосипед — используйте стандартные исключения если они подходят. Не логируйте и не пробрасывайте одновременно. Всегда добавляйте контекст (ID заказа, логин).

Когда стоит создавать свои исключения?

Создавать кастомные исключения стоит тогда, когда стандартных недостаточно, чтобы однозначно описать проблему предметной области и позволить вызывающему коду принять осмысленное бизнес-решение.

Три главных критерия (когда точно ДА)

1. Специфическая реакция клиента. Вызывающий код должен различать ошибки и действовать по-разному.

try {
    paymentService.charge(card, amount);
} catch (InsufficientFundsException e) {
    redirectToTopUpPage();
} catch (CardExpiredException e) {
    askForNewCard();
} catch (GatewayTimeoutException e) {
    scheduleRetry(e);
}

2. Дополнительный контекст, важный для обработки. Ошибка несёт данные, которые нужны клиенту для восстановления или логирования.

3. Моделирование предметной области (иерархии). Когда ошибки образуют естественную иерархию.

Когда НЕ стоит

СитуацияИспользуйте
Невалидный аргумент методаIllegalArgumentException
Объект в неподходящем состоянииIllegalStateException
Операция не поддерживаетсяUnsupportedOperationException
Нет специфической реакции клиентаСтандартное исключение с хорошим сообщением

Прагматичное правило

Создавайте кастомное исключение, если есть хотя бы два разных способа отреагировать на ошибку в зависимости от её типа.

Что лучше: наследоваться от Exception или RuntimeException?

Выбор зависит от того, кто виноват в проблеме и может ли клиент её исправить.

Правило 1: Если вызывающий код может осмысленно восстановиться — Exception.

Правило 2: Если ошибка программиста или нарушение контракта API — RuntimeException.

Современный тренд: чаще использовать RuntimeException, чтобы не засорять сигнатуры. Без четкой необходимости восстановления лучше начинать с RuntimeException.

Что такое оборачивание (wrapping) исключений?

Оборачивание — это паттерн, при котором исключение одного типа перехватывается и пробрасывается дальше как исключение другого типа с сохранением исходного в качестве причины (cause).

1. Как это выглядит

// Без оборачивания: SQLException просачивается через все слои
public void saveUser(User user) throws SQLException { ... }

// С оборачиванием: каждый слой говорит на своём языке
public void saveUser(User user) {
    try {
        // низкоуровневый код
    } catch (SQLException e) {
        throw new DataAccessException("Failed to save user: " + user.getId(), e);
    }
}

2. Зачем это нужно

  1. Сокрытие деталей реализации: вызывающий код не должен знать, что вы используете JDBC
  2. Сохранение цепочки причин: исходное исключение доступно через getCause()
  3. Преобразование checked → unchecked: для совместимости с лямбдами и Stream API

3. Антипаттерны

Потеря причины, пустое сообщение, многослойное оборачивание, оборачивание + логирование на каждом слое.

4. Когда оборачивать НЕ нужно

Если клиенту нужно различать конкретные типы исключений, если это граница одного модуля, если исключение уже имеет нужный уровень абстракции.

Почему не стоит глотать исключения (catch empty)?

Пустой catch-блок скрывает факт ошибки, делая систему непредсказуемой. Это одна из самых опасных практик в Java.

1. Что такое "глотание"

// Антипаттерн: пустой catch
try { criticalOperation(); }
catch (Exception e) { }

// Антипаттерн: printStackTrace() в продакшене
catch (Exception e) { e.printStackTrace(); }

// Антипаттерн: return null без индикации ошибки
catch (IOException e) { return new Configuration(); }

2. Цепочка последствий

Реальная проблема: база данных недоступна. Ближайшее проявление: NPE через 5 слоёв абстракции. Время на диагностику: часы вместо минут. Корректное состояние приложения: потеряно.

3. Скрупулёзный разбор всех последствий

  • Потеря контекста ошибки: исключение содержит точное место сбоя, стек-трейс, причину
  • Распространение некорректного состояния: программа продолжает работу с частично инициализированными данными
  • Каскадное накопление ошибок: одна проглоченная ошибка порождает другие
  • Утечка ресурсов: connection, statement, resultSet остались открыты
  • Детерминированный баг становится недетерминированным

4. Исключения из правила (очень редкие)

finally-подобная очистка (best effort), прерывание спящего потока (с восстановлением флага!), специфические системные вызовы с ложными сбоями. Любое исключение должно сопровождаться комментарием.

5. Правильные альтернативы

Проброс с сохранением контекста, логирование на верхнем уровне, try-with-resources для ресурсов, Optional для ожидаемых отсутствий.

🟡 Диагностика

Что такое stack trace?

Stack trace — это снимок состояния стека вызовов потока в момент создания объекта-исключения (Throwable). Он показывает полный путь выполнения: цепочку методов от точки входа в поток до места, где произошла ошибка.

1. Что именно он содержит

// Типичная строка stack trace:
// at com.example.service.PaymentService.charge(PaymentService.java:42)

public final class StackTraceElement {
    public String getClassName();   // com.example.service.PaymentService
    public String getMethodName();  // charge
    public String getFileName();    // PaymentService.java
    public int    getLineNumber();  // 42
}

2. Когда и как создаётся

Критически важный момент: Stack trace заполняется в момент вызова конструктора Throwable, а не в момент throw. Именно поэтому создание исключений — относительно дорогая операция.

3. Причины и подавленные исключения

В Java 7+ stack trace также учитывает Cause (причина) и Suppressed (подавленные исключения).

4. Антипаттерны

e.printStackTrace() в продакшене, log.error(e.getMessage()) без самого e, создание исключений ради stack trace.

Что делает метод printStackTrace()?

printStackTrace() — это метод класса Throwable, который выводит полную информацию об исключении в стандартный поток ошибок System.err: тип исключения, сообщение, трассировку стека, цепочку причин и подавленные исключения.

1. Что именно выводится

Exception in thread "main" java.lang.RuntimeException: Outer error
    at com.example.Service.outer(Service.java:20)
    at com.example.Main.main(Main.java:5)
Caused by: java.io.IOException: File not found
    at com.example.Service.readFile(Service.java:30)
    ... 1 more
    Suppressed: java.sql.SQLException: Connection closed
        at com.example.Service.close(Service.java:35)

2. Почему это не для продакшена

Выводит в System.err — неструктурированный поток, который не попадает в файлы логов, не имеет временных меток и контекста, теряется в контейнерах. Правильно — логировать через логер.

3. Когда использование оправдано

Отладка в IDE, одноразовые скрипты и утилиты, демонстрационные примеры и учебный код. В любом production-коде — только через логер.

Как правильно логировать исключения?

Золотое правило: Передавайте сам объект исключения в метод логгера, а не его сообщение (getMessage()) или результат printStackTrace().

// ❌ Неправильно -- стектрейс потерян
log.error("Payment failed: " + e.getMessage());
e.printStackTrace();

// ✅ Правильно -- объект исключения отдельным аргументом
log.error("Failed to process payment for order {}", orderId, e);

1. Три главных правила

  1. Исключение — всегда последним аргументом. Любой современный логгер распознаёт Throwable и автоматически добавляет полный стектрейс.
  2. Контекст важнее сообщения. Всегда включайте ключевые параметры (orderId, userId, gateway).
  3. Не логируйте и не пробрасывайте одновременно. Ошибка должна быть залогирована ровно один раз — в том слое, который её окончательно обрабатывает.

2. Нестандартные ситуации

Checked исключение, которое не ошибка: WARN ("Could not delete temporary file"). Событие безопасности: всегда WARN. Отказ внешнего сервиса: ERROR + детали.

3. Уровни логирования

4. Структурированное логирование (JSON)

Современный тренд — логи в JSON для автоматического парсинга системами мониторинга (Logstash, Elasticsearch).
