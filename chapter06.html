🔷 Интерфейсы Collection Framework

Какие основные интерфейсы Collection Framework?

Краткий ответ: Collection Framework построен на трёх корневых интерфейсах: Collection<E>, Map<K,V> и Iterator<E>. От Collection наследуются List, Set и Queue.

Полная иерархия интерфейсов

Iterable<E>
    │
    └── Collection<E>
            │
            ├── List<E>          — упорядоченная, доступ по индексу, дубликаты
            ├── Set<E>           — уникальность, нет дубликатов
            │   └── SortedSet<E> — отсортированные
            │       └── NavigableSet<E> — навигация
            └── Queue<E>         — FIFO
                ├── Deque<E>     — двусторонняя (FIFO + LIFO)
                └── BlockingQueue<E> — потокобезопасная с блокировкой

Map<K,V>                          — отображение (НЕ наследует Collection)
    ├── SortedMap<K,V>
    │   └── NavigableMap<K,V>
    └── ConcurrentMap<K,V>

📌 Резюме для Middle+

Collection Framework — это фундамент Java-разработки. Три корневых интерфейса (Collection, Map, Iterator) определяют контракты для всех структур данных. Map стоит особняком — не наследует Collection, потому что работает с парами ключ-значение, а не с отдельными элементами. Каждый интерфейс имеет свои контракты по поводу порядка, дубликатов, null-значений и потокобезопасности, что позволяет выбрать правильную структуру под задачу. Понимание этой иерархии — база для выбора между ArrayList, HashSet, TreeMap и другими реализациями.

В чём разница между List, Set и Queue?

Краткий ответ: List — упорядоченная коллекция с доступом по индексу и дубликатами. Set — уникальные элементы без индексов. Queue — FIFO-коллекция для временного хранения перед обработкой.

Когда что использовать

List<String> history = new ArrayList<>();

// Set — уникальность и быстрая проверка наличия

// Queue — обработка в порядке поступления

📌 Резюме для Middle+

List, Set и Queue — три базовых контракта интерфейса Collection, каждый для своего сценария. List даёт полный контроль над позицией элемента (индексы) и сохраняет порядок вставки с дубликатами. Set гарантирует уникальность и оптимизирован для быстрой проверки наличия элемента, жертвуя индексацией. Queue моделирует поведение очереди (FIFO) и оптимизирован для сценариев "производитель-потребитель", добавляя специальные методы с разной реакцией на пустоту/переполнение. Выбор интерфейса определяет не только доступные методы, но и контракт, которому должны следовать все реализации.

🟠 List и реализации

В чём разница между ArrayList и LinkedList?

Краткий ответ: ArrayList — динамический массив (O(1) доступ, O(n) вставка в середину). LinkedList — двусвязный список (O(n) доступ, O(1) вставка/удаление на концах).

Внутреннее устройство

// ArrayList — динамический массив
transient Object[] elementData; // непрерывный блок памяти
// LinkedList — двусвязный список
private static class Node<E> { E item; Node<E> next; Node<E> prev; }

📌 Резюме для Middle+

ArrayList — динамический массив с O(1) доступом по индексу, плотным хранением и эффективной итерацией (кеш-локальность). Платное — вставка/удаление не в конец: O(n) на сдвиг элементов через System.arraycopy(). LinkedList — двусвязный список с O(1) вставкой/удалением в начале и конце, но O(n) доступом по индексу и значительным оверхедом по памяти (объекты Node с двумя ссылками). Главный практический вывод для Middle+: в 95% случаев ArrayList — правильный выбор. LinkedList имеет смысл только когда нужна функциональность Deque (очередь/стек) или когда доказано профилировщиком, что вставка/удаление в начале списка — узкое место.

🎯 Что показать на собеседовании
  • Развеять миф: "вставка в середину LinkedList быстрее" — оба O(n), но System.arraycopy() в ArrayList часто быстрее обхода указателей в LinkedList из-за кеш-промахов
  • Объяснить кеш-локальность: элементы ArrayList лежат в непрерывном блоке памяти (L1/L2/L3 кеш процессора), элементы LinkedList разбросаны по куче (кеш-промах на каждом узле)
  • Сравнить память: 1M элементов ArrayList ≈ 4MB (только ссылки), LinkedList ≈ 4MB + 24MB на Node
  • Упомянуть RandomAccess: ArrayList помечен этим интерфейсом, LinkedList — нет (сигнал алгоритмам использовать get(i) или Iterator)
  • Показать реальный бенчмарк: вставка в середину 100K элементов — ArrayList ~0.3ms, LinkedList ~0.7ms
Когда использовать ArrayList, а когда LinkedList?

Краткий ответ: ArrayList — в 95% случаев (чтение по индексу, вставка в конец). LinkedList — когда нужны частые вставки/удаления в начале или используется как очередь/стек.

// ArrayList — много чтения, вставка в конец
List<User> users = new ArrayList<>();
// LinkedList — очередь/стек, вставка в начало
LinkedList<Task> tasks = new LinkedList<>();
tasks.addFirst(new UrgentTask()); // O(1)

Главный миф: вставка в середину LinkedList НЕ быстрее ArrayList (оба O(n), но System.arraycopy часто быстрее).

Когда LinkedList — правильный выбор

// 1. Нужна функциональность Deque (двусторонняя очередь)
Deque<Task> deque = new LinkedList<>();
// 2. Много вставок/удалений в начале (ДОКАЗАНО профилировщиком)
// 3. Не нужен доступ по индексу
📌 Резюме для Middle+

ArrayList — выбор по умолчанию. LinkedList оправдан когда нужна функциональность Deque или когда профилировщик доказывает, что вставка/удаление в начале списка — узкое место. Замена LinkedList на ArrayList — один из самых частых перфоманс-фиксов в Java-приложениях. Для очередей и стеков современной альтернативой LinkedList является ArrayDeque — он быстрее и потребляет меньше памяти.

  • Упомянуть, что в стандартной библиотеке Java LinkedList используется редко, ArrayList — повсеместно

Краткий ответ: get(i) — O(1), add(E) в конец — O(1) амортизированное, add(i, E) — O(n), remove(i) — O(n), contains/indexOf — O(n), set(i, E) — O(1).

Краткий ответ: get(i) — O(n), addFirst/addLast — O(1), add(i, E) в середину — O(n), removeFirst/removeLast — O(1), remove(i) — O(n), contains — O(n).

📌 Резюме для Middle+

LinkedList — двусвязный список с O(1) операциями на концах благодаря прямым ссылкам на first и last. Доступ по индексу — O(n) с оптимизацией (обход от ближайшего конца). Главный практический вывод: LinkedList имеет преимущество перед ArrayList только при частых операциях в начале списка и при использовании как Deque. Вставка в середину — O(n) в обоих случаях, но ArrayList обычно быстрее из-за кеш-локальности и нативного System.arraycopy().

Что такое Vector и чем он отличается от ArrayList?

Краткий ответ: Vector — устаревшая (legacy) реализация динамического массива из Java 1.0, все методы synchronized. ArrayList — современная реализация из Java 1.2, не синхронизирована. В современной разработке Vector не используется.

ПроизводительностьВысокаяНизкая

📌 Резюме для Middle+

Vector — устаревшая синхронизированная реализация из Java 1.0. В современной разработке не используется: для однопоточного кода — ArrayList (быстрее без синхронизации), для многопоточного — Collections.synchronizedList() или CopyOnWriteArrayList. Даже в многопоточной среде Vector неудобен, потому что составные операции (check-then-act) всё равно требуют внешней синхронизации. Единственное место, где Vector всё ещё встречается — legacy-код и Swing (DefaultListModel).

Что такое Stack?

Краткий ответ: Stack — устаревшая реализация LIFO-стека из Java 1.0, наследующая Vector. В современной Java заменяется на ArrayDeque с методами push(), pop(), peek().

// ✅ Правильный стек в современной Java
Deque<String> stack = new ArrayDeque<>();
stack.push("A"); stack.push("B"); stack.push("C");
stack.peek(); // "C"
stack.pop();  // "C"

Почему Stack устарел: наследование от Vector нарушает инкапсуляцию (доступен любой элемент по индексу), все методы synchronized (оверхед), есть современная альтернатива ArrayDeque.

📌 Резюме для Middle+

Stack — устаревшая реализация LIFO из Java 1.0. Из-за наследования от Vector нарушается инкапсуляция (доступен любой элемент через методы Vector), синхронизация всех методов снижает производительность. Правильная замена — ArrayDeque с методами push(), pop(), peek(). ArrayDeque быстрее, соблюдает инкапсуляцию и не содержит устаревшего наследия. Для многопоточного стека — ConcurrentLinkedDeque или внешняя синхронизация ArrayDeque.

  • Продемонстрировать правильную замену — ArrayDeque с push/pop/peek

  • Сравнить Stack, ArrayDeque и LinkedList как стека в таблице

Queue — интерфейс FIFO-коллекции с двумя наборами методов (бросающие исключения vs возвращающие специальные значения). Ключевые реализации: ArrayDeque — оптимальный выбор для однопоточной очереди (быстрее LinkedList, меньше памяти); LinkedList — когда дополнительно нужен доступ по индексу; PriorityQueue — очередь по приоритету на основе кучи (не FIFO); ConcurrentLinkedQueue — потокобезопасная без блокировок; реализации BlockingQueue — для producer-consumer с блокировкой. Что такое Deque?

Краткий ответ: Deque (Double Ended Queue) — интерфейс двусторонней очереди, позволяющий добавлять/удалять элементы с обоих концов. Может работать как FIFO, LIFO или двусторонняя очередь.

Три режима использования

// FIFO-очередь
Deque<String> queue = new ArrayDeque<>();
queue.offerLast("A"); queue.pollFirst(); // "A"
// LIFO-стек
Deque<String> stack = new ArrayDeque<>();
stack.push("A"); stack.pop(); // "A"
// Двусторонняя
deque.addFirst(urgent); deque.addLast(normal);

Основная реализация — ArrayDeque (циклический массив, быстрее LinkedList, не разрешает null). Является рекомендуемой заменой Stack и LinkedList в роли очереди.

📌 Резюме для Middle+

Deque — интерфейс двусторонней очереди, расширяющий Queue. Позволяет работать в трёх режимах: FIFO-очередь (offerLast/pollFirst), LIFO-стек (push/pop), двусторонняя очередь. Основная реализация — ArrayDeque (циклический массив, быстрее LinkedList, меньше памяти, не разрешает null). Является рекомендуемой заменой для Stack и для LinkedList в роли очереди. На собеседовании важно знать оба набора методов и три режима использования.

🟢 Set и реализации

В чём разница между HashSet, LinkedHashSet и TreeSet?

Краткий ответ: HashSet — без гарантий порядка (O(1), на HashMap). LinkedHashSet — порядок вставки (O(1), на LinkedHashMap + двусвязный список). TreeSet — отсортированный порядок (O(log n), на красно-чёрном дереве).

Как работает HashSet внутри?

Краткий ответ: HashSet — обёртка над HashMap. Элементы становятся ключами HashMap, значения — единый объект-заглушка PRESENT.

// Внутреннее устройство
private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();

public boolean add(E e) { return map.put(e, PRESENT) == null; }
public boolean contains(Object o) { return map.containsKey(o); }
public boolean remove(Object o) { return map.remove(o) == PRESENT; }

Все операции делегируются HashMap. Производительность: O(1) в среднем. Требования к элементам такие же, как к ключам HashMap (equals/hashCode, неизменяемость).

📌 Резюме для Middle+

HashSet — это тонкая обёртка над HashMap. Элементы множества — ключи HashMap, значения — единый объект-заглушка PRESENT. Все операции делегируются соответствующим методам HashMap. Благодаря этому HashSet наследует все свойства HashMap: O(1) в среднем, деревофикация при коллизиях в Java 8+, зависимость от качества hashCode(), "потеря" элемента при изменении после добавления. Ключевое: понимание внутреннего устройства (HashMap с заглушкой), почему при итерации порядок не гарантирован, и почему требования к элементам такие же, как к ключам HashMap.

Что такое TreeSet и как он работает?

Краткий ответ: TreeSet — реализация Set на основе красно-чёрного дерева (TreeMap). Хранит элементы в отсортированном порядке, все операции O(log n). Реализует NavigableSet с методами навигации.

TreeSet<Integer> set = new TreeSet<>();
set.add(5); set.add(1); set.add(3);
// [1, 3, 5] — всегда отсортирован

// Методы навигации
set.first();        // 1 — минимальный
set.last();         // 5 — максимальный
set.lower(3);       // 1 — строго меньше 3
set.higher(3);      // 5 — строго больше 3
set.headSet(3);     // [1] — все < 3
set.tailSet(3);     // [3, 5] — все ≥ 3

Определяет уникальность по compareTo()/compare(), а не по equals().

📌 Резюме для Middle+

TreeSet — реализация Set на основе красно-чёрного дерева (TreeMap). Гарантирует отсортированный порядок элементов (по Comparable или Comparator), все базовые операции за O(log n). Реализует NavigableSet с методами навигации. В отличие от HashSet/LinkedHashSet, определяет уникальность по compareTo()/compare(), а не по equals()/hashCode(), что может приводить к расхождению с контрактом Set. Не допускает null. Выбор между TreeSet и HashSet — компромисс между O(log n) с сортировкой и O(1) без порядка.

Когда использовать TreeMap?

Краткий ответ: Когда нужна автоматическая сортировка ключей или операции с диапазонами (subMap, tailMap, headMap, min/max, ближайший больший/меньший). Если сортировка не нужна — HashMap (O(1) вместо O(log n)).

// Операции с диапазонами

scores.lastKey();      // максимальный ключ
scores.higherKey(70);  // ближайший больший 70

Если сортировка не нужна, HashMap даёт лучшую производительность. Если нужен порядок вставки — LinkedHashMap. Если ключи — enum — EnumMap ещё быстрее HashMap. Что такое WeakHashMap?

Краткий ответ: WeakHashMap — Map, в которой ключи хранятся как WeakReference. Если на ключ нет сильных ссылок, GC удаляет запись. Полезно для кешей без риска memory leak.

Map<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "value");
key = null; System.gc(); // запись удалена!

// ⚠️ Строковые литералы НИКОГДА не удалятся (String Pool)
📌 Резюме для Middle+

WeakHashMap — специализированная Map со слабыми ссылками (WeakReference) на ключи. Когда на ключ нет сильных ссылок, GC удаляет запись. Идеально для кешей без риска memory leak: метаданные классов, временные ассоциации, канонические отображения. Важные ограничения: значения — сильные ссылки; строковые литералы не удалятся (String Pool); удаление не мгновенное (зависит от GC); не потокобезопасен. Главное преимущество перед HashMap — предотвращение memory leak при хранении временных ассоциаций.

Как ConcurrentHashMap обеспечивает thread-safety?

Краткий ответ: Три механизма: CAS для вставки в пустые корзины (lock-free), synchronized на голове корзины для занятых корзин, volatile-чтение для get() без блокировок.

// 1. Пустая корзина → CAS (без блокировки)
if (tabAt(tab, i) == null) {

}
// 2. Занятая корзина → synchronized на голове
synchronized (f) { /* обход и вставка */ }
// 3. Чтение → volatile, без блокировок
public V get(Object key) { return ...; }

🟣 Потокобезопасные коллекции

Что такое CopyOnWriteArrayList?

Краткий ответ: Потокобезопасный список, при каждой модификации создающий новую копию внутреннего массива. Чтение без блокировок. Оптимален когда чтений значительно больше, чем записей.

// Идеален для: списков слушателей, конфигураций
private final CopyOnWriteArrayList<EventListener> listeners = 
    new CopyOnWriteArrayList<>();
for (EventListener l : listeners) { l.onEvent(event); } // без блокировок
listeners.add(newListener); // копирование массива (редко)
📌 Резюме для Middle+

CopyOnWriteArrayList — потокобезопасный список, оптимизированный для сценариев "много чтений, редкие записи". При каждой модификации создаёт новую копию внутреннего массива под ReentrantLock, атомарная замена через volatile. Чтение без блокировок. Итераторы — snapshot, не бросают ConcurrentModificationException. Главный недостаток — дороговизна модификаций (O(n) копирование). Идеален для списков слушателей, конфигураций. Непригоден для частых модификаций или больших списков.

Когда использовать synchronized collections?

Краткий ответ: Когда нужно быстро добавить потокобезопасность к существующей коллекции, и при этом чтения и записи примерно равны, а потоков немного. Для высоконагруженных сценариев — конкурентные коллекции.

// Быстрая синхронизация
List<String> syncList = Collections.synchronizedList(new ArrayList<>());

// ⚠️ Составные операции требуют внешней синхронизации
synchronized (syncList) {
    if (!syncList.contains("key")) syncList.add("key");
}
// ⚠️ Итерация требует внешней синхронизации
synchronized (syncList) {
    for (String s : syncList) { process(s); }
}
📌 Резюме для Middle+

Collections.synchronized*() — быстрый способ сделать коллекцию потокобезопасной, обернув все методы в synchronized. Подходит для сценариев с умеренной конкуренцией. Ключевые недостатки: необходимость внешней синхронизации для составных операций и итерации; глобальная блокировка снижает производительность при высокой конкуренции. В современной разработке предпочтительнее конкурентные коллекции. На собеседовании важно показать понимание ограничений и умение выбрать правильную коллекцию.

Что такое Collections.unmodifiableList()?

Краткий ответ: Создаёт неизменяемую обёртку (view) вокруг списка. Методы чтения работают, методы модификации выбрасывают UnsupportedOperationException. Не копирует данные.

List<String> unmodifiable = Collections.unmodifiableList(original);
unmodifiable.add("X"); // UnsupportedOperationException!
// ⚠️ Это обёртка, не копия! Изменения оригинала видны
📌 Резюме для Middle+

Collections.unmodifiableList() создаёт неизменяемую обёртку (view), не копируя данные. Это быстрый способ защитить коллекцию от изменений через возвращаемую ссылку, но он не защищает от изменений через оригинальную ссылку и не делает элементы неизменяемыми. Для полной защиты — List.of() (Java 9+) или List.copyOf() (Java 10+). На собеседовании важно различать обёртку (view) и копию.

🟡 Итераторы

В чём разница между Iterator и ListIterator?

Краткий ответ: Iterator — базовый для однонаправленного обхода любых коллекций. ListIterator — расширенный только для List, с обходом в обоих направлениях, добавлением и заменой элементов.

Iterator — базовый интерфейс для однонаправленного обхода (вперёд, remove()), доступен для всех коллекций. ListIterator расширяет Iterator для двунаправленного обхода списков (вперёд/назад, add(), set(), индексы). Ключевые отличия: ListIterator работает только с List; позволяет обход в обратном направлении; поддерживает добавление и замену элементов. Курсор ListIterator находится между элементами, а не на них.

Что такое fail-fast и fail-safe итераторы?

Краткий ответ: Fail-fast выбрасывают ConcurrentModificationException при изменении коллекции после создания итератора. Fail-safe не бросают исключений (snapshot или weakly-consistent).

ХарактеристикаFail-FastFail-Safe
Исключение при изменении✅ ConcurrentModificationException❌ Нет
Как работаетПроверка modCountСнимок (snapshot) или слабая согласованность
ПримерыArrayList, HashSet, HashMapCopyOnWriteArrayList, ConcurrentHashMap
📌 Резюме для Middle+

Fail-fast итераторы — стандартное поведение большинства коллекций Java. Они выбрасывают ConcurrentModificationException при обнаружении структурного изменения, используя счётчик modCount. Это механизм раннего обнаружения багов в однопоточном коде, но не гарантия потокобезопасности. Fail-safe итераторы не бросают исключений: snapshot-based (CopyOnWriteArrayList) работают с копией данных, weakly-consistent (ConcurrentHashMap) обходят актуальные данные без гарантии видеть все изменения.

Что такое ConcurrentModificationException?

Краткий ответ: Исключение, выбрасываемое fail-fast итераторами при обнаружении структурного изменения коллекции во время итерации. Не связано напрямую с многопоточностью — чаще возникает в одном потоке при неправильном удалении.

// Классический пример
for (String s : list) {
    if (s.equals("B")) list.remove(s); // ConcurrentModificationException!
}
// Правильно — Iterator.remove()
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("B")) it.remove(); // OK
}
📌 Резюме для Middle+

ConcurrentModificationException — fail-fast исключение при расхождении modCount и expectedModCount в итераторе. Вопреки названию, не связано с многопоточностью — чаще возникает в одном потоке. Правильные способы модификации: Iterator.remove(), removeIf(), обход по индексу в обратном направлении. Fail-safe коллекции не бросают это исключение. На собеседовании важно объяснить внутренний механизм и правильные паттерны удаления.

Как правильно удалять элементы во время итерации?

Краткий ответ: (1) Iterator.remove(), (2) removeIf() (Java 8+), (3) обратный обход по индексу для List, (4) removeAll()/retainAll().

// Способ 1: Iterator.remove()
Iterator<String> it = list.iterator();
while (it.hasNext()) { if (it.next().equals("B")) it.remove(); }
// Способ 2: removeIf (Java 8+)
list.removeIf(s -> s.equals("B"));
// Способ 3: Обратный обход
for (int i = list.size() - 1; i >= 0; i--) {
    if (list.get(i).equals("B")) list.remove(i);
}
📌 Резюме для Middle+

Правильное удаление при итерации зависит от сценария. Iterator.remove() — универсальный способ. removeIf() (Java 8+) — лаконичный для удаления по условию. Обратный обход по индексу — только для List. Массовые операции (removeAll, retainAll) — для набора элементов. Ключевое правило: никогда не использовать методы коллекции во время итерации, кроме как через сам итератор.

🟠 Comparable и Comparator

Что такое Comparable и Comparator?

Краткий ответ: Comparable — интерфейс для естественного порядка (метод compareTo()), реализуется самим классом. Comparator — интерфейс для внешнего порядка (метод compare()), реализуется отдельно.

// Comparable — естественный порядок внутри класса
public class User implements Comparable<User> {
    @Override public int compareTo(User other) { return name.compareTo(other.name); }
}
// Comparator — внешний порядок (лямбда)
Comparator<User> byAge = Comparator.comparingInt(User::getAge);
users.sort(byAge);
📌 Резюме для Middle+

Comparable (один метод compareTo(), один естественный порядок) реализуется внутри класса. Comparator (один метод compare(), множество порядков) реализуется отдельно, не требует изменения класса, и позволяет создавать цепочки сортировок. Java 8+ сделала Comparator основным инструментом благодаря функциональному интерфейсу и лаконичным статическим методам. На собеседовании важно объяснить разницу на примерах.
