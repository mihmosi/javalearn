🟣 Антипаттерны

Что такое антипаттерны?

Антипаттерны — это распространённые, но неудачные решения типичных задач, которые сначала кажутся правильными, но со временем приводят к сложному сопровождению, ошибкам, плохой производительности или высокой связанности кода.

Если паттерн проектирования — это проверенное хорошее решение, то антипаттерн — это решение, которое часто встречается на практике, но создаёт проблемы в долгосрочной перспективе.

К чему приводят антипаттерны

  • сильная связанность компонентов
  • сложное тестирование
  • плохая расширяемость
  • большое количество ошибок
  • снижение производительности
  • трудное сопровождение

Антипаттерн vs Code Smell

Code Smell — это признак возможной проблемы в коде (симптом). Например, слишком длинный метод или дублирование. Он не всегда означает ошибку, но сигнализирует, что код стоит пересмотреть.

Антипаттерн — это уже известное неудачное архитектурное или проектное решение (причина), которое систематически приводит к проблемам.

Как бороться

  • принципы SOLID
  • рефакторинг
  • code review
  • модульные тесты
  • статический анализ (SonarQube, SpotBugs, Checkstyle)
  • соблюдение архитектурных правил
👹 God Object (Blob)

Самый известный антипаттерн. Один класс делает всё: работает с БД, валидирует данные, отправляет email, рассчитывает стоимость, логирует, управляет транзакциями.

// ❌ God Object — один класс делает всё
class UserService {
    void saveUser() { /* БД */ }
    void sendEmail() { /* Email */ }
    void calculateDiscount() { /* Скидки */ }
    void printInvoice() { /* Печать */ }
    void exportExcel() { /* Экспорт */ }
    void uploadFile() { /* Загрузка */ }
    void validateData() { /* Валидация */ }
    void logActivity() { /* Логирование */ }
    void manageTransaction() { /* Транзакции */ }
}

Почему плохо

  • нарушается Single Responsibility Principle
  • сложно тестировать — нужно мокать десятки зависимостей
  • любое изменение может затронуть множество функций
  • класс становится огромным (тысячи строк)
  • несколько разработчиков не могут работать с классом параллельно
// ✅ Разделение ответственности
class UserRepository { void save(User user) {} }
class EmailService { void sendWelcome(User user) {} }
class DiscountCalculator { BigDecimal calculate(User user) {} }
class InvoicePrinter { void print(Order order) {} }
class UserValidator { void validate(User user) {} }

// Координирующий сервис — тонкий, только оркестрация
class UserRegistrationService {
    private final UserRepository repo;
    private final EmailService email;
    private final UserValidator validator;

    public void register(User user) {
        validator.validate(user);
        repo.save(user);
        email.sendWelcome(user);
    }
}
🍝 Spaghetti Code

Код без понятной структуры: длинные методы, множество вложенных if, запутанные зависимости, непонятный поток выполнения.

// ❌ Spaghetti Code
public void process(Order order) {
    if (order != null) {
        if (order.getStatus() == "NEW") {
            if (order.getAmount() > 0) {
                if (checkInventory(order)) {
                    order.setStatus("PAID");
                    if (order.getUser() != null) {
                        if (order.getUser().getEmail() != null) {
                            sendEmail(order.getUser().getEmail());
                        } else {
                            if (order.getUser().getPhone() != null) {
                                sendSms(order.getUser().getPhone());
                            }
                        }
                    }
                }
            }
        }
    }
}

Признаки

  • глубокая вложенность (стрелка вправо — стрела ада)
  • методы на сотни строк
  • смешение уровней абстракции
  • циклические зависимости
  • трудно понять, что делает код
// ✅ Рефакторинг: выделение методов, Guard Clauses
public void process(Order order) {
    if (order == null) throw new IllegalArgumentException("Order is null");
    if (!order.isNew()) return;
    if (!order.hasPositiveAmount()) return;

    if (inventoryService.reserve(order)) {
        order.markAsPaid();
        notifyUser(order.getUser(), "Order confirmed");
    }
}

private void notifyUser(User user, String message) {
    if (user.getEmail() != null) {
        emailService.send(user.getEmail(), message);
    } else if (user.getPhone() != null) {
        smsService.send(user.getPhone(), message);
    }
}

Решение

  • рефакторинг: выделение методов
  • Guard Clauses вместо вложенных if
  • применение паттернов проектирования (Strategy, State)
  • соблюдение SOLID
🔨 Golden Hammer

"Если у тебя есть молоток — всё кажется гвоздём." Разработчик использует один инструмент для всех задач.

Примеры

  • везде применяет Singleton, даже где не нужен
  • любую задачу решает через наследование вместо композиции
  • использует микросервисы там, где достаточно монолита
  • применяет сложные паттерны к простым задачам
// ❌ Golden Hammer: Singleton для всего
class UserValidator { /* Singleton */ }
class PriceCalculator { /* Singleton */ }
class EmailFormatter { /* Singleton */ }
// Все классы — синглтоны, даже утилиты без состояния

Решение: выбирать инструмент под задачу, а не наоборот. Оценивать контекст, сложность и требования перед выбором решения.

📋 Copy-Paste Programming

Одинаковый код копируется во множество мест.

// ❌ validateUser() скопирован в 15 классов
class UserController {
    boolean validateUser(User user) {
        if (user.getName() == null || user.getName().isEmpty()) return false;
        if (user.getEmail() == null || !user.getEmail().contains("@")) return false;
        return true;
    }
}
class OrderService {
    boolean validateUser(User user) { /* ТОТ ЖЕ КОД */ }
}
class PaymentService {
    boolean validateUser(User user) { /* ТОТ ЖЕ КОД */ }
}

Проблема

  • исправление ошибки требует менять код в каждом месте
  • легко пропустить одно из мест при обновлении
  • кодовая база раздувается
  • нарушается DRY (Don't Repeat Yourself)
// ✅ Выделить общий код
public class UserValidator {
    public static boolean isValid(User user) {
        if (user.getName() == null || user.getName().isEmpty()) return false;
        if (user.getEmail() == null || !user.getEmail().contains("@")) return false;
        return true;
    }
}
// Использование во всех классах
UserValidator.isValid(user);
🔢 Magic Numbers / Magic Strings

Появляются непонятные значения: if (status == 7) или if ("ADMIN".equals(role)). Непонятно: почему именно 7, что означает "ADMIN".

// ❌ Magic Numbers
if (user.getStatus() == 3) { ... }
if (order.getAmount() > 10000) { ... }
Thread.sleep(3000); // что за 3000?
connection.setTimeout(5000); // что за 5000?

// ❌ Magic Strings
if ("ADMIN".equals(role)) { ... }
if (response.getCode().equals("ERR_001")) { ... }
// ✅ Именованные константы и enum
enum UserStatus { NEW(1), ACTIVE(2), BLOCKED(3); }

if (user.getStatus() == UserStatus.BLOCKED) { ... }

private static final BigDecimal VIP_THRESHOLD = new BigDecimal("10000");
if (order.getAmount().compareTo(VIP_THRESHOLD) > 0) { ... }

private static final int CONNECTION_TIMEOUT_MS = 5000;
connection.setTimeout(CONNECTION_TIMEOUT_MS);
💎 Singleton Abuse

Сам по себе Singleton — не антипаттерн. Но злоупотребление им приводит к проблемам: все сервисы сделаны Singleton и обращаются друг к другу через глобальное состояние.

// ❌ Все сервисы — синглтоны, зависят друг от друга через getInstance()
class OrderService {
    public void create(Order order) {
        Database.getInstance().save(order);
        Logger.getInstance().log("Order created");
        EmailService.getInstance().send(order.getUser(), "Confirmed");
        Cache.getInstance().invalidate("orders");
    }
}

Проблемы

  • сложно тестировать — нельзя подменить моками
  • скрытые зависимости — не видно, что нужно сервису
  • нарушение DIP — зависимость от конкретных классов
  • жёсткая связанность — замена Logger требует изменений везде
// ✅ Dependency Injection
@Service
class OrderService {
    private final Database database;
    private final Logger logger;
    private final EmailService emailService;
    private final Cache cache;

    // Зависимости явно видны в конструкторе
    public OrderService(Database database, Logger logger,
                        EmailService emailService, Cache cache) {
        this.database = database;
        this.logger = logger;
        this.emailService = emailService;
        this.cache = cache;
    }
}
🟤 Big Ball of Mud

Большой проект без архитектуры. Все классы зависят друг от друга, циклические зависимости, невозможно понять структуру системы.

Признаки

  • циклические зависимости между пакетами
  • невозможно выделить слои приложения
  • любое изменение вызывает ошибки в неожиданных местах
  • нет чётких границ между модулями
  • тесты не проходят после любого рефакторинга

Как возникает

Проект долго развивается без архитектурного контроля. Каждый разработчик добавляет код "как получится". Нет code review, нет рефакторинга, нет общих правил.

Решение: архитектурный контроль, выделение модулей, построение диаграмм зависимостей, постепенный рефакторинг, инструменты вроде ArchUnit для проверки архитектурных правил.

🌋 Lava Flow

В проекте остаётся старый код, который никто не удаляет. Причины: "вдруг пригодится", никто не знает используется ли он, страх сломать что-то.

// ❌ Примеры Lava Flow
@Deprecated // висит годами
public void oldMethod() { ... }

// Класс не используется, но все боятся удалить
class LegacyReportGenerator { ... }

// Закомментированный код
// if (oldFlag) { doSomethingOld(); }

Результат

  • мёртвый код занимает место
  • лишние классы усложняют навигацию
  • сложнее понимать систему
  • новые разработчики пытаются использовать устаревший код

Решение: регулярно удалять неиспользуемый код, полагаться на систему контроля версий (Git) для истории, использовать анализаторы (IntelliJ IDEA показывает unused code), покрывать код тестами перед удалением.

⚡ Premature Optimization

"Преждевременная оптимизация — корень многих проблем." Разработчик начинает оптимизировать код без измерений.

// ❌ Оптимизация без профилирования
// Использует сложные структуры данных без необходимости
Map<String, List<Integer>> cache = new ConcurrentHashMap<>();
// Пишет низкоуровневые оптимизации
int result = (a << 1) + b; // вместо a * 2 + b
// Использует примитивы вместо объектов для экономии на Boxing
// ✅ Правильный подход
// 1. Сделать код понятным
int result = a * 2 + b;

// 2. Измерить производительность (профилирование)
// 3. Оптимизировать только узкие места
// 4. Повторить измерение для проверки эффекта
📌 Hard Coding

Данные жёстко прописаны в коде.

// ❌ Hard Coding
String url = "jdbc:mysql://192.168.1.100:3306/mydb";
int timeout = 3000;
String apiKey = "sk-1234567890abcdef";
String adminEmail = "admin@company.com";
int maxRetries = 3;
// ✅ Вынос в конфигурацию
// application.properties
database.url=jdbc:mysql://localhost:3306/mydb
database.timeout=3000
api.key=${API_KEY}
notification.admin-email=admin@company.com
retry.max-attempts=3

// Использование
@Value("${database.url}")
private String databaseUrl;

@Value("${retry.max-attempts}")
private int maxRetries;

Куда выносить

  • application.properties / application.yml
  • переменные окружения (секреты, ключи API)
  • конфигурационные классы
  • Consul / Vault / AWS Parameter Store
☕ Антипаттерны, специфичные для Java

1. == вместо equals()

// ❌ Сравнение ссылок вместо содержимого
if (user.getRole() == "ADMIN") { ... } // false, если строка не из пула
if (new Integer(100) == new Integer(100)) { ... } // может быть false
// ✅ Правильное сравнение
if ("ADMIN".equals(user.getRole())) { ... }
if (Objects.equals(a, b)) { ... }

2. Использование null вместо Optional

// ❌ Возврат null
public User findUser(Long id) {
    return null; // вызывающий код должен помнить про проверку
}
// ✅ Optional для явного указания возможности отсутствия
public Optional<User> findUser(Long id) {
    return Optional.ofNullable(user);
}

3. Чрезмерное использование статических методов

// ❌ Статические методы везде — глобальное состояние
class Util {
    static void doSomething() {}
    static void doAnother() {}
    static void doMore() {}
}

4. Слишком длинные методы (Long Method)

Методы на сотни строк, делающие множество разных вещей. Решение: выделение подметодов (рефакторинг Extract Method).

5. Исключения для обычной логики

// ❌ Исключения для управления потоком
try {
    Integer.parseInt(s);
} catch (NumberFormatException e) {
    return 0;
}

6. Неправильное использование многопоточности

// ❌ Общий ArrayList без синхронизации
List<String> list = new ArrayList<>();
// Поток 1: list.add("a");
// Поток 2: list.add("b");
// Результат непредсказуем
// ✅ Потокобезопасные коллекции
List<String> list = new CopyOnWriteArrayList<>();
List<String> list = Collections.synchronizedList(new ArrayList<>());

7. God Class с большим количеством полей

Класс с десятками полей и обязанностей. Решение: разделить на несколько классов по ответственности.
